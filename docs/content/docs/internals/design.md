For contributors: why devvm is built the way it is, what was tried and dropped, and what's still open. How each part works is on its own page; the layout and rules are in [AGENTS.md](https://github.com/w3cj/devvm/blob/main/AGENTS.md).

## Emulated features

When devvm builds a backend feature from other parts of the backend, the feature is [emulated](backends.md#features), and it gets a note here before its review. The note says what the feature is built from, the guarantee it keeps, what could break it, and which end-to-end checks prove it. The threat check comes next, and only then is the feature marked reviewed. Every feature Lima has is native except its ports, which devvm's forwarder emulates ([below](#ports-on-lima)).

### Network policy on smolvm

**The guarantee:** as on Lima, a VM with network policy reaches nothing but its own proxy, even as root, and a refused DNS query never leaves the host, but for one narrow channel, a query for `devvm.invalid` (the DNS channel, under Not covered below). Reviewed: the threat check's findings are fixed or listed below, and the end-to-end checks prove the rest.
**What it's built from**, all set by `Start` while the machine is stopped:

- **An allow list of the gateway alone** (`--reset-allow-list --allow-cidr 100.96.0.1/32`): smolvm refuses TCP to any other address, IPv6 included, and UDP but DNS. The gateway is every port of the host's loopback, so the allow list alone isn't enough.
- **DNS closed** (`--allow-host-pattern devvm.invalid`): smolvm's resolver, which takes every DNS query on port 53 whatever its address (UDP or TCP), answers NXDOMAIN itself for any other name, without asking anyone. `--dns` would be simpler, but `machine update` can't change it.
- **devvm's proxy as the decider** (`machine start --mediated-egress --egress-interceptor 127.0.0.1:PORT`, its token in `SMOLVM_INTERCEPTOR_TOKEN`): before smolvm connects anywhere, it sends the proxy's decider (`devvm _proxy -decider`, on a host loopback port of its own) the connection's destination and first bytes. The decider takes over only connections to the proxy's own address in the VM (`100.96.0.1:<proxy port>`): the same connection then carries it, and the proxy serves it as any other, password and policy included. It refuses every other connection the allow list lets through (another port of the host's), logged as `blocked` (`TCP`, refused). smolvm connects nowhere itself for a VM's TCP.
- **The token**: 32 random bytes, new at each start, kept in the VM's state and a file of the proxy's (mode 600), never in a process's arguments, never in the VM. It goes one way only: smolvm sends it to the decider at the start of each connection, and the decider proves nothing back. So it protects the decider from others: a program on the host that connects to the decider's port without it gets no answer, and can't have the proxy take over a connection of its own as the VM's (the decider reads nothing past the token without it, and at most 8 KiB of first bytes with it). It doesn't protect smolvm from a fake decider (below). A proxy restarted while the VM runs gets the same port and token.
- **Confined** compares the machine's `agent.pid` (its process and start time) with the one recorded after devvm's start through the decider, checks that process runs, and that the allow lists smolvm reports are still the ones above: smolvm changes them on a running machine (`smolvm machine update --allow-cidr`), which makes the VM `unenforced`, and its next launch stops it. A start without network policy removes the allow list and the decider requirement (`--net --reset-allow-list --no-egress-interceptor`).

**What it relies on:** smolvm's virtio-net gateway enforcing the allow list, the mediated-egress decision (protocol version 2) before any upstream connection and failing closed when the decider is gone or answers badly, its resolver's hostname filter, and the requirement it records: once a machine started through a decider, smolvm refuses a start without one (`smolvm machine start` by itself fails). None of it is in the VM, so root there can't change it.

**What could break it:** a smolvm release that changes the protocol, stops recording the requirement, or lets a connection through before the decision (each fails the end-to-end checks); a program on the host that takes the decider's port while the proxy is down: smolvm sends it the token and lets it decide. Protocol version 2 has a third verdict, `0`, allow direct, which a squatter could give, but smolvm refuses a direct connection to the host (`direct_target_policy`), and the allow list admits nothing else; what a squatter can do is take connections over (`2`) and carry them anywhere itself (checked: such a decider answers the probe), as on Lima a program that takes the proxy's port gets the VM's traffic. A decider that answers garbage, or nothing, refuses (checked). It starts before the VM, so it's down only while it's restarted (new rules, a new devvm) or once it fails; a start that finds a port taken, or fails, stops the VM (`net_proxy_down_stopped`), on Lima too, but whatever took the port meanwhile decided for it until then. Someone on the host who starts the machine with a decider of their own isn't confined: devvm reports it `unenforced` and stops it.

**Not covered:**

- smolvm's JSON (`machine ls`, `machine status`) shows only the allowed CIDRs and host patterns, not its UDP allows (`--allow-udp`), deny lists or egress rules (API only), and `--reset-allow-list` leaves UDP allows in place (`--remove-allow-udp` needs each one by name). Someone on the host who adds a UDP allow, live or not, lets the VM send UDP there, past the decider, and devvm can't see it (checked: one added live lets an NTP request out). Only the host's user can. A UDP allow of the gateway still doesn't reach the host's loopback.
- ICMP to the gateway (ping) passes; to anywhere else it gets no answer (checked; smolvm's own network doesn't forward ICMP either, so that check has no control).
- **A DNS channel:** a query for `devvm.invalid` itself is forwarded to smolvm's upstream resolver, by default the host's first nameserver, usually on the network. The name is fixed, but the VM chooses when to ask, the query type, the name's case and EDNS options: a narrow way out to whoever sees that resolver's traffic. It can't be closed from here: smolvm takes only valid DNS names as patterns and forwards every allowed one, `localhost` included (with a black-hole upstream, `devvm.invalid`, `localhost`, `localhost.localdomain` and `local` all waited on it), and the upstream is set only by `machine create --dns`, for every query, with policy or without. Closing it would take `--dns` at create pointing at a resolver devvm runs (port 53 on the host's loopback, which only root can take; `0.0.0.0:53` is open to users but to the network too), or a VM's network policy fixed when it's made.
- The proxy's own limits ([Not covered](../safety/network.md#not-covered)). Linux hosts are untested.

**End-to-end checks** (`tests/e2e.sh --backend smolvm`):

- the VM runs behind its proxy and decider and passes the self-check; its allow list and DNS are as above; an allowed host works through the proxy, others get `403`;
- direct connections fail even as root (an address, a port of an allowed host, IPv6, a service on the host's loopback through the gateway); on smolvm's own network the same probes get out, their control;
- DNS fails at once. While the VM resolves names of its own (through its resolver, and straight to the gateway's resolver and `1.1.1.1` over UDP and TCP: A, TXT, ANY, AAAA, HTTPS, EDNS0, a name under `devvm.invalid`), smolvm's process has no flow beyond the host's loopback (nettop, macOS), and smolvm's own decision log (`egress-decisions.jsonl`) refuses every name; `DEVVM.INVALID`, sent too, is the channel's own name and is let through, as nothing but `devvm.invalid` is. nettop is blind to queries smolvm forwards under a hostname filter (it asks through the system's resolver), so the log is the detector, and a query for `devvm.invalid`, which it does forward, is the control that the log sees one. On smolvm's own network, nettop sees the probe's queries leave;
- UDP and ICMP: datagrams to a host loopback listener through the gateway, to `1.1.1.1` on 443 and 123, and an NTP request reach nothing, and a ping to `1.1.1.1` gets no answer; a UDP allow added live lets the NTP request out, and on smolvm's own network nettop sees the datagrams leave (their controls);
- the token is in no host process's arguments and nowhere in the VM, and the proxy's password in no host process's arguments; `devvm log` shows the proxy's blocks and the refused connections to the host; `devvm policy allow` and `rm` apply at once;
- an allow list widened while the VM runs makes it `unenforced`, and devvm stops it, then starts it confined;
- with the proxy gone, or a decider of nobody's that answers garbage, nothing or allow direct, nothing gets out (the host's loopback listener included), while one that takes connections over answers the probe (its control), and `smolvm machine start` refuses the machine; started with someone else's decider, devvm stops it; `devvm network off` and `on` switch it to smolvm's own network and back.

### ssh for editors on smolvm

**The guarantee:** as on Lima, ssh and editors reach a smolvm VM by name, that VM alone (host keys of its own, read through smolvm and pinned), only as the VM's user and only with that VM's own key; and an ssh session devvm's entry makes gives the VM no way out it doesn't already have (with network policy, nothing past its proxy), whatever the VM runs as sshd: the host's ssh asks for nothing that would carry it, and the entry pins the options that could. Reviewed, in two rounds: the threat check's findings are fixed or listed below (the entry's options, a key per VM, no host keys read before sshd runs, ports that never collide, an image without sshd), and the end-to-end checks prove the rest.
**What it's built from:**

- **sshd in base:** `sshd.sh`, as root after base's scripts, installs `openssh-server` from the archive they left (Ubuntu's snapshot: from the live archive, before them, its systemd libraries were newer than the snapshot's packages layers install, Docker's, could match), keeps the snapshot's package lists for layers, and deletes the host keys its package made; `prepare.sh` sets the user's password to `*` (none matches; sshd without PAM refuses a locked `!` account's keys too). Both are in base's key.
- **Only when asked for:** the caller sets `Confinement.SSH` at each start of a project VM when `Require` lets `ssh` through (always: it's reviewed); builds never ask. Without it the start removes the forward and runs no sshd, `SSH` answers `vm_no_ssh`, and the ssh config skips any backend whose `ssh` isn't usable (`Review.Allowed`).
- **The forward:** `machine update -p PORT:22` while the machine is stopped. `PORT` is `Confinement.SSHPort`, the `ssh_port` devvm records in the VM's state with or without network policy. Without one, it's the port the machine had while that's free on `127.0.0.1` and `::1`, else a new one. It's never one of the VM's listed ports: `ssh_port` avoids every VM's listed ports and is picked again when it's one of the VM's, and the backend refuses one that is anyway (`smolvm_ssh_port_forwarded`). smolvm binds it on the host's loopback alone, and its forwards reach only servers on all addresses, so sshd listens on `0.0.0.0:22` (IPv4). It's the only forward of smolvm's a VM has, because devvm's forwarder forwards the VM's own ports ([ports](#ports-on-smolvm)).
- **sshd, after each start** (`services.sh`, as root): every host key deleted and a new ed25519 one made, so no two VMs from one pack share one, nor a VM's starts; devvm's public key as the only authorized key (`/etc/devvm/ssh/authorized_keys`, root's); a config of devvm's own (`/etc/devvm/ssh/sshd_config`, mode 600, `sshd -f`, checked with `sshd -t` first), whatever the image's says: `AllowUsers` the VM's user, `PermitRootLogin no`, `AuthenticationMethods publickey`, passwords and keyboard-interactive off, `AllowTcpForwarding local`, `AllowStreamLocalForwarding local`, `PermitListen none`, `GatewayPorts no`, `X11Forwarding no`, `PermitTunnel no`, `PermitUserEnvironment no`, `AllowAgentForwarding yes`; it listens on IPv4 alone (`ListenAddress 0.0.0.0:22`) and connects local forwards to IPv4 or IPv6 (`AddressFamily any`, for [the forwarder](#ports-on-smolvm)'s servers on `::1`). A failure stops the VM, but an image without sshd (made before devvm installed one; asked first, with a probe of its own, so no other failure reads as it) starts without ssh, warned (`vm_no_sshd`; a VM made after `devvm rebuild` has it). The record says the start's sshd runs (`ssh_up`, cleared before each start, set once `services.sh` is done), and `SSH` answers only then: a devvm that runs meanwhile can't read, and pin, the host keys this start is about to replace.
- **The sessions' environment:** sshd on its own config runs without PAM, so `SetEnv` gives sessions `/etc/environment` (`BASH_ENV`) and the variables `Start` names (the proxy's, `NO_PROXY`, the CA files'), whose values `services.sh` reads from its own environment: the proxy file's (`--secret-file`) and the machine's, never in arguments. Login shells also read `/etc/profile.d`, as devvm's do.
- **The VM's key:** ed25519, made in Go in OpenSSH's format at the VM's first start with ssh, `~/.local/share/devvm/smolvm/vms/<vm>.key` (mode 600, one file written whole; its public half is read back from it, never kept apart), deleted with the VM. Its public half, passed to `services.sh`, is that VM's only authorized key: one VM's key logs in to no other. `SSH` returns `127.0.0.1`, the port, the user, and `IdentityFile` with `IdentitiesOnly yes` and `PreferredAuthentications publickey`: the user's agent keys aren't offered to the VM.
- **Pinning** is the shared code's, as on Lima: a VM's keys are forgotten before each start and read after it with `cat /etc/ssh/ssh_host_*_key.pub` through `Exec` (smolvm's `machine exec`, which reaches the VM itself, not over the network), and entries check them (`HostKeyAlias`, `StrictHostKeyChecking yes`).

**What keeps a session from carrying the VM out.** An ssh session can carry the VM's traffic only through channels the host's ssh asks for: remote forwards (`-R`, `RemoteForward`, a remote SOCKS forward), X11, a tunnel and the agent; OpenSSH's client refuses a channel the server opens unasked. Root in the VM runs whatever sshd it likes, so the guarantee is the host's ssh's: devvm's entry (first in `~/.ssh/config`, so its options win over a `Host *`) sets `ForwardX11 no`, `ForwardX11Trusted no`, `Tunnel no`, `PermitRemoteOpen none` (so devvm needs OpenSSH 8.7 or newer; no `IgnoreUnknown` for older ones, as its first value wins and would replace a user's `Host *` one, such as macOS's for `UseKeychain`), `ForwardAgent` as the agent choice the VM's current start was made with says ([below](#ssh-agent-forwarding-on-docker)), `AddKeysToAgent no` (no key of the host's lands in an agent the session forwards), `ProxyJump none` and `ProxyCommand none` (no hop through something else), `UpdateHostKeys no` (the VM can't add host keys; devvm reads them itself) and `HashKnownHosts no`. Shared with Lima. A `RemoteForward` can't be turned off without refusing `ssh -R` on the command line too, so it isn't (Not covered). VS Code's Remote-SSH uses local and dynamic forwards (`-L`, `-D`) and is unaffected. Then sshd's own settings, a defence for an honest VM, and the same on Lima (`assets/layers/base.sh`, `/etc/ssh/sshd_config.d/00-devvm.conf`, first so it wins; Lima's own forwards are local; it applies only where the image's `sshd_config` includes `sshd_config.d`, as Ubuntu's and Debian's do, so for some `--from` images not at all, which only an honest VM's defence loses):

- **Local forwarding** (`-L`, `-D`, `-W`) is allowed: the VM itself connects, from its own network, which network policy confines like any other connection of the VM's (checked). VS Code's Remote-SSH reaches its server this way.
- **Remote forwarding is refused,** ports and sockets: the host would connect on the VM's behalf to anything it reaches, its loopback services and sockets (`docker.sock`, agents) included, around network policy. So are X11 and tunnels.
- **Agent forwarding** is allowed: the entry decides it from the SSH agent choice the VM's current start was made with (`ForwardAgent`, devvm's own agent too), as on Lima; refusing it would break `devvm ssh-agent on` in editors.

These settings guard against the host's ssh asking for a forward that devvm's entry doesn't pin (a `RemoteForward` under `Host *`, `ssh -R`), and only while root in the VM leaves sshd as it is.

**What it relies on:** smolvm binding forwards on the host's loopback alone and carrying them under mediated egress, which decides only the VM's own connections; `machine exec` reaching the VM itself; OpenSSH's client refusing unrequested channels; devvm's `Include` line first in `~/.ssh/config`, so its entries' options win.

**What could break it:** a smolvm release that binds forwards beyond the loopback (the network could reach sshd: still key-only); host ssh settings that come before devvm's entries (as on Lima); a program on the host that takes the port while the VM is stopped (there's no entry for a stopped VM, a start whose port is taken fails, and the pinned host key refuses any other server).

**Not covered:**

- A remote forward you ask for (`ssh -R`, a `RemoteForward` of yours) into a VM whose root allowed it: sshd's settings are the VM's to change, and the entry can't refuse it. Don't forward into a VM you don't trust.
- **DNS detection:** a machine with any port forward of smolvm's (its ssh's) runs on smolvm's virtio-net network, as one with an allow list always does; without one, on TSI, where the VM asks this machine's resolver itself (checked: `nameserver 10.0.0.1` vs `100.96.0.1`, and a TSI machine can't have a forward). On virtio-net, smolvm's resolver asks through the system's resolver, which nettop can't tie to the VM, so smolvm's decision log, with `devvm.invalid` as its control, is network policy's only DNS detector there, with or without a forward. nettop's DNS control (the queries seen to leave) is a TSI machine's, and every devvm VM has a forward now, so e2e runs it on a machine of its own from base's pack, without one. (The no-leak check ran both with and without a forward before ssh was reviewed, and held both ways; smolvm writes its decision log only with a decider, so a machine of e2e's own can't repeat the one without.) A host-side detector for virtio-net would take root (a packet capture) or a canary zone ([manual checks](../contributing/testing.md#manual-checks)).
- Sessions see the proxy's password, as devvm's own shells do; what VS Code relays ([VS Code](../using/ssh.md#vs-code)) is as on Lima.
- Other users on the host reach the port (the host's loopback): they get the host key, and no login.
- Linux hosts are untested.

**End-to-end checks** (`tests/e2e.sh --backend smolvm`):

- an entry by the folder's name, its port on the host's loopback alone; the machine's process listens on its ssh forward's alone, with ports listed or not; the net backend pinned: virtio-net (`nameserver 100.96.0.1`) with a forward, with network policy or without, TSI (this machine's resolver) on a machine without one;
- an image without sshd (root moved it away): the next start warns `vm_no_sshd` and runs, without an entry, `devvm ssh` says so; sshd back, a start has ssh again;
- the pinned host key is the VM's own, ed25519, its only one; a changed one is refused; a restart makes a new one, pinned again; another VM from the same image has its own, and its own port;
- `ssh` by name reaches the VM's user with `BASH_ENV`; the agent isn't forwarded whatever `Host *` says; passwords and keyboard-interactive are refused, publickey alone offered; another key, `root` and another user are refused, devvm's key is the control;
- remote forwarding (a port, the host's agent socket) is refused, a local forward works; `sshd -T` shows the settings above, and the config is root's alone, mode 600;
- a hostile sshd (root rewrites its config to allow remote forwarding, X11, tunnels, and restarts it), reached through a `Host *` that asks for X11 and to add keys to the agent: no display in the session and no key in the agent; the same asked for on the command line (`-X`, `-o AddKeysToAgent=yes`) gets both (the controls), and `ssh -R` then works (what isn't covered); `ssh -A` forwards the agent (the agent-off check's control);
- a recorded port squatted while the VM is stopped: its next start forwards another, and ssh reaches it; another VM's key doesn't log in to it;
- `devvm ssh`, `devvm code` (a stub `code`), `devvm stop` (no entry, nothing on the port), `rm` (entry and keys gone);
- `--clone`: the clone pushed in over ssh, every branch, nothing of the folder mounted; fetching the VM's commit and pushing a branch through devvm's ssh config; `rm -f` keeping the fetched work;
- with network policy: ssh on the VM's `ssh_port`, sessions (a login's or not) with the proxy's settings, an allowed host through the proxy; a local forward to `1.1.1.1:80` or a service on the host's loopback gets nothing back, remote forwarding is refused, a direct connection from a session fails; after `devvm network off`, the same local forward gets an answer (the control); network policy's DNS no-leak check runs with the forward (DNS detection above).

### Ports on smolvm

**The guarantee:** when a VM forwards every port, each TCP port from 1024 up that a server in it listens on, on its loopback or on all its addresses, is forwarded to the same port on the host's loopback, and only to its loopback. When a VM lists its ports, only those are forwarded, however many it lists, by the same rules. The forwarder never takes a port that a program on the host has on any address when the forward is made, or a port devvm records for a VM. Forwarding gives the VM no way out that it doesn't already have, because every connection starts on the host, so with network policy the VM still reaches nothing past its proxy. The emulation is reviewed, with the threat check's findings fixed or listed below, which is why the host key read is capped, reports are paced and the log is limited, and the end-to-end checks prove the rest. Listed ports use the same forwarder with `-only`, as on [Docker](#ports-on-docker) and [Lima](#ports-on-lima), so the threat check's findings for every port hold for them, and the leads that are their own are in the threat check for listed ports below.

**What it's built from:**

- **None of smolvm's forwards.** devvm makes a VM with no `-p` but its ssh's, whatever ports it forwards, and `SetPorts` changes only devvm's record of them, then starts a running VM's forwarder again with them. smolvm's own forwards would need each port at create or update while the machine is stopped, allow at most 64 of them, reach only servers on all addresses, and share a port that a host program has on every address (`SO_REUSEADDR`), taking that program's loopback connections.
- **Only when allowed.** The caller requires `ports` or `ports-all` with `Review.Require` when the VM is made or its ports are set, and warns when it lets them through. It checks again at each start with `Review.Allowed`, and refuses the start otherwise, so a VM made while the emulation was let through doesn't start once it isn't. Because the emulation is reviewed, it's always let through. The backend then runs a forwarder at each start of a VM whose record says every port (`ports_all`) or lists ports (`listed_ports`).
- **A forwarder per VM, on the host.** The forwarder is `vmssh.Forwarder`, which [Docker's ports](#ports-on-docker) and [Lima's](#ports-on-lima) also use, and on smolvm it runs as `devvm _smolvm-ports`. `Start` starts it detached once `services.sh` has run the VM's sshd ([ssh](#ssh-for-editors-on-smolvm)), and `SetPorts` starts it again on a running VM, each after stopping any forwarder the VM had, which ends the connections open through it. devvm finds that one by its pid file, which it checks against the process's arguments, as it does for the proxy. It sends that forwarder SIGTERM and kills it if it hasn't ended within 2 s, so its ports are free before devvm asks which listed ports a host program has. devvm holds a lock of the VM's own (`<vm>.ports.lock`, beside its pid file) from stopping the old forwarder until the new one has started, so two devvm runs at once, such as a start and `devvm ports`, leave one forwarder, the one its pid file names. A machine started outside devvm since devvm's last start has no sshd of devvm's, so `SetPorts` starts no forwarder for it and devvm warns with `ports_no_ssh`. `Start` waits up to 10 s for the forwarder to say it forwards. If it doesn't, devvm warns with `ports_forward_failed`, naming its log, and leaves it to keep trying while the VM runs on. A VM without ssh forwards nothing, and devvm warns with `ports_no_ssh`. The forwarder ends when the machine's process does. It follows the same lifeline as the proxy, `agent.pid`, and exits once that process is gone or a new start has changed the file's contents. `stop` and `Delete` stop it first.
- **Reaching the VM.** The forwarder makes one ssh connection, a master (`ssh -F none -M -S <socket>`), to the port on the host's loopback that the VM's sshd is forwarded from. It logs in as the VM's user with the VM's own key alone (`IdentitiesOnly`, `IdentityAgent=none`). It reads the VM's host key through smolvm each time it starts, after a start of the VM or a change of its ports, as root, with `machine exec … cat /etc/ssh/ssh_host_ed25519_key.pub`. Because the VM decides what that prints, devvm reads at most 64 KiB of it, for at most 30 s. The key goes into a known_hosts file of the forwarder's own and is pinned with `HostKeyAlias` and `StrictHostKeyChecking yes`. The master reads none of the user's configuration and forwards nothing either way, with `ClearAllForwardings`, `PermitRemoteOpen none`, `ProxyCommand none`, and no agent, X11 or tunnel. Its control socket is in `~/.local/share/devvm/run` (mode 700) and is named by a hash of the VM's name, because a socket's path is at most 104 characters. When the connection is lost, the forwarder closes its forwards and makes the connection again every 2 s while the lifeline holds.
- **What listens.** The master's session runs `ports.sh` as the VM's user (`sh -s`). It prints the local addresses of the VM's listening TCP sockets, which are the state `0A` lines of `/proc/net/tcp` and `tcp6`, whenever they change and every 10 s regardless, so it ends soon after the connection does. The forwarder treats the report as untrusted. A line over 128 bytes or a report over 4096 lines ends the connection, and anything that isn't a hex address and port is skipped. Reports are applied at least 500 ms apart, and one that comes sooner waits, holding up the VM's ssh channel with it, so the VM can't make the forwarder bind, dial and read devvm's state at its own pace. The VM can make the forwarder write to its log, with ports coming and going and with the session's stderr, so the log takes 200 writes at once and then one every 10 s. Each write is at most 512 bytes, with control characters shown as `?`, and a start empties the log once it's over 1 MiB. A forwarded port's connections go to `127.0.0.1` for a server on all IPv4 addresses or on that address, and to `::1` for a server on all IPv6 addresses or on that address. A server on another `127.x` address alone gets its connections there. Servers on other addresses alone aren't forwarded.
- **Which ports.** With every port, the forwarder takes ports from 1024 up, because the ports below are the host's system services. With listed ports, it takes those alone (`-only`), a listed port below 1024 included, because the user asked for it, and a bind the host refuses is logged. The listed ports are the record's less those `Confinement.Free` leaves out, which are the ports a program on the host has when the forwarder starts, as on every backend, with a `ports_taken` warning. `Free` is asked once the VM's old forwarder has stopped, so the VM's own forwards don't read as taken, and when no port is left, no forwarder runs. Either way the forwarder takes at most 256 ports at once, and it never takes a reserved port. The reserved ports are the VM's own ssh, proxy and decider ports, and every VM's ssh, proxy and decider ports and other VMs' listed ports as their state records them (`netpolicy.UsedPorts`). The forwarder reads them again each time it would take a port, and while it can't read them, it takes no new port. A smolvm VM without network policy keeps its ssh port only in its smolvm record. smolvm holds that port while the VM runs, but while the VM is stopped another VM's forwarder can take it, and the VM's next start then forwards ssh from another port. The pinned host key refuses any other server on the old one. A port the forwarder couldn't take is tried again only once the VM's server on it goes and comes back.
- **Listening.** The forwarder listens on `127.0.0.1` and `::1`, or on IPv4 alone on a host without IPv6. It binds without `SO_REUSEADDR` (`platform.ListenExclusive`). With that option, which Go and smolvm set, macOS lets a socket take `127.0.0.1:PORT` while a program has `*:PORT`, and that program's loopback connections go with it. Without the option, the bind is refused when another program has the port on any address. This was checked on macOS for a program on `0.0.0.0`, on `::` (IPv4 and IPv6 at once, as Node's and Go's servers listen), on IPv6 alone and on `127.0.0.1`, each with and without `SO_REUSEADDR` of its own. A port held only by ended connections (`TIME_WAIT`, with nothing answering on it) is taken as usual, so a server that restarts gets its forward back. When a bind is refused, the forwarder dials the port and takes it only if the dial is refused. A full backlog times out, which counts as taken. A port the forwarder took on `127.0.0.1` but finds in use on `::1` is given up, so `localhost` never reaches two programs. On Linux, `SO_REUSEADDR` stays on. Linux refuses that bind with the option too while another socket listens on the port, and without it, the forwarder's own ended connections (`TIME_WAIT`) would keep anyone from listening on the port for a minute, its next forwarder included. This was checked on Docker's Linux engine.
- **Each connection.** Each forwarded connection is a channel of the master's (`ssh -S <socket> -W HOST:PORT`), with one process per connection and at most 256 at once. The VM's sshd opens it to the VM's own loopback from inside the VM, so sshd connects over IPv4 or IPv6 (`AddressFamily any`) while still listening on IPv4 alone. The channel's ssh has the master's options. If the master is gone, ssh connects on its own, and it then reaches the VM's sshd the same way, never the host's.

**What keeps a forward from carrying the VM out.** Every connection starts on the host. A program connects to the forwarder's port, and the forwarder asks the VM's sshd to connect to the VM's loopback. The VM opens nothing to the host through the forwarder, because the master asks for no remote forward, agent, X11 or tunnel, and OpenSSH's client refuses a channel that the server opens unasked, whatever sshd root in the VM runs. What the VM sends back goes to the program that connected, as with any forward. The VM's own connections, including sshd's to its loopback, belong to the VM's own network, which network policy confines as usual. The forwarder never takes the VM's proxy or decider port, so while the proxy is gone, a server in the VM can't take the place of the decider smolvm asks, or of another VM's decider while that one is down.

**What it relies on:** the VM's sshd and its pinned host key, which come from the [ssh](#ssh-for-editors-on-smolvm) emulation. It also relies on OpenSSH's client refusing unrequested channels and honoring `-F none`, on smolvm binding the ssh forward on the host's loopback alone, on the kernel refusing a bind without `SO_REUSEADDR` where another socket has the port (checked on macOS), and on devvm's state listing every VM's ports.

**What could break it:** a smolvm release that binds the ssh forward beyond the loopback, which still lets in only the VM's key. Another is devvm's state being lost or unreadable for a VM whose proxy port is then free, which the forwarder handles by forwarding no new port while it can't read the state.

**Threat check for listed ports** (the security-audit skill, its local IPC companion). The forwarder and its transport are the ones checked for every port, so these leads are what listed ports add, each confirmed or ruled out:

- **A port the VM chooses:** ruled out. `-only` comes from devvm's record for the VM, less what `Confinement.Free` leaves out, both on the host, and the VM's reports can't add to it. A listed port is forwarded only while a server in the VM listens on it, as with every port.
- **smolvm's own forwards:** ruled out. devvm makes and updates a machine with no `-p` but its ssh's, so a listed port is never one of smolvm's, which would share a host program's port (`SO_REUSEADDR`). The end-to-end checks look at the machine's process, which listens on its ssh forward alone, with listed ports and with network policy.
- **A listed port that is the VM's ssh forward:** ruled out. The ssh forward's host port is never one of the VM's listed ports. A port the VM had is given up when it's listed, the VM's `ssh_port` is picked again when it's listed, and the backend refuses one that's listed anyway (`smolvm_ssh_port_forwarded`). The forwarder also reserves the ssh port, which smolvm holds while the VM runs.
- **Port 22 listed:** ruled out as a collision. Port 22 in the VM is its sshd, and the ssh forward comes from another host port, so a listed 22 forwards the VM's sshd to the host's port 22 as it would forward any server. The VM's sshd still takes only the VM's own key, as the VM's user. A host whose own sshd has port 22 keeps it, with a `ports_taken` warning. The end-to-end checks list 22 with network policy, and ssh by name still reaches the VM from its own port.
- **A listed proxy or decider port:** ruled out. The forwarder reserves the VM's own proxy and decider ports whether or not they're listed, and every other VM's as well.
- **A listed port below 1024:** taken because the user asked for it. A host service that has the port keeps it, and a bind the host refuses is logged. One that isn't running yet is under **Not covered**.
- **More ports than smolvm forwards:** ruled out. smolvm's limit of 64 forwards doesn't apply because smolvm forwards none of them, and the forwarder takes at most 256 at once.
- **A forwarder left behind:** ruled out. `stop` and `Delete` stop it, `Delete` removes its files, and a start or change whose listed ports are all taken runs none. Two devvm runs that start a VM's forwarder at once take turns on the VM's lock, so the second stops the first one's forwarder, and neither leaves one that its pid file doesn't name, which nothing would stop.
- **Network policy:** ruled out. Listed ports take fewer ports than every port, never more, and every connection still starts on the host. The end-to-end checks prove that direct connections fail with listed ports too.

**Not covered:**

- A VM can take a free port from 1024 up, or a listed one, on the host's loopback that a program there expects to be its own, such as one that isn't running yet or is restarting. What the VM serves there reaches whatever connects, so a page it serves to the user's browser can reach the internet from the host, past network policy.
- A host program that starts on a port while the VM has it forwarded still binds it when it listens on all addresses with `SO_REUSEADDR`, as most servers do (checked on macOS). Its loopback connections then reach the VM, because the forward's address is the narrower one. A program that binds without `SO_REUSEADDR` is refused.
- The VM can make the forwarder dial a host loopback port that's in use and then close the connection at once without sending anything, because that's how the forwarder checks for a port held only by ended connections. This happens at most once per port every second, as the VM's listener on the port goes and comes back.
- Servers only on the VM's other addresses, such as its network address or a container's, aren't forwarded.
- Other users on the host reach the forwards, because they're on the host's loopback.
- UDP isn't forwarded on any backend. [Ports](../using/ports-size.md#ports) shows how to tunnel it over TCP.
- A server that keeps a port while its forward couldn't be made, because the host had the port, isn't forwarded until it stops and starts again.
- Linux hosts are untested.

**End-to-end checks** (`tests/e2e.sh --backend smolvm`):

- The machine's process listens on its ssh forward alone. The forwarder's ssh master reads no config, offers the VM's key alone with its host key pinned, and asks for no forwarding.
- Servers on the VM's `127.0.0.1`, on `::1`, on all IPv4 addresses and on all addresses each answer at the host's `127.0.0.1` and `::1`, and the forwarder listens on the host's loopback alone.
- A port that a host program has on every address stays the host program's, and the VM's server on it isn't forwarded. A port below 1024 isn't forwarded. The host program also keeps its port when it's on the host's `127.0.0.1` alone, on its `::1` alone (so `localhost` never reaches two programs), or on `::`, which is IPv4 and IPv6 at once. A server on the VM's own network address alone isn't forwarded, and neither is a port another VM's state lists while it's free, while a loopback server is forwarded as the control. A server that stops loses its forward, and the others stay.
- `devvm stop` stops the forwarder and closes its ports. A new start has a new forwarder, which forwards a server started then, and `rm` deletes the forwarder and its files.
- With listed ports, the machine's process still listens on its ssh forward alone, and the forwarder runs with the listed ports alone (`-only`). A listed port's server on all addresses, and one on the VM's loopback alone, each answer at the host's loopback, while an unlisted port's server on the VM's loopback doesn't. A listed port that a host program has on every address is left out with a `ports_taken` warning, its localhost connections stay the host program's while a listed port's server is forwarded as the control, and once the program is gone the next start forwards the port again.
- On a running VM, a port that `devvm ports add` lists has its server reach the host at once, and once `devvm ports rm` takes it out, it doesn't. The machine's process is the same throughout, so the VM never restarted.
- With network policy, the self-check passes and a server's port is forwarded, while direct connections still fail, even as root. With the proxy and decider gone and the VM listening on their ports, neither port is forwarded, while a port of the VM's own is forwarded as the control, and the next devvm starts the proxy on those ports again. With network policy and listed ports, 22 among them, the self-check passes, the machine's process listens on its ssh forward alone, which isn't port 22, and ssh by name reaches the VM. The forwarder runs with the listed ports alone, a listed port's server answers while an unlisted one's doesn't, and direct connections still fail.

### SSH agent toggling on smolvm

**The guarantee:** as on Lima, `devvm ssh-agent on`, `devvm` or `off` changes an existing VM's agent from its next start, and every start devvm makes (a launch, `restart`, an export's, `rm`'s check of a `--clone` VM) gives the VM only the agent its choice names: with `devvm`, devvm's own and never yours; with `off`, no agent at all, so the VM, root included, lists no keys, adds none and signs nothing, and reaches no agent of anyone's through smolvm's. A VM started some other way, which may have an agent devvm didn't choose, is stopped when devvm next finds it running. Reviewed: the threat check's one finding, a VM you start yourself, is fixed that way (the lifeline check below); the rest is listed below, and the end-to-end checks prove it.
**What it's built from:**

- **Forwarding from the start:** smolvm sets forwarding only at `machine create --ssh-agent` (`machine update` has no option for it). A VM made while `agent-toggle` is let through (`VMSpec.AgentToggle`, from `Review.Require`, warned when unreviewed) is made with it whatever its choice, and its state records that it relies on the emulation (`agent_toggle=on`). The backend's record keeps both: made forwarding (`forwarding`), and the choice being none (`agent_off`), which `SetAgentForwarding` sets on a stopped VM; `Inspect` reports forwarding only when made so and not off.
- **The agent, at each start:** smolvm's process reads `SSH_AUTH_SOCK` when the machine starts and connects to that path again for each of the VM's connections to `/tmp/ssh-agent.sock` (checked: a socket made at the path after the start is reached, a missing one gives the VM `communication with agent failed`, and a start without `SSH_AUTH_SOCK` fails). `Start` sets it alone: none for one made without forwarding; `/dev/null/devvm-no-agent` when the record or the start's `Confinement.NoAgent` says none (either is enough, so a start that skips the launch's `SetAgentForwarding`, as an export's does, still gives none); else `Confinement.AgentSocket` (devvm's own); else devvm's own `SSH_AUTH_SOCK` (yours); with none, `smolvm_no_agent` before anything changes. Your agent or devvm's is chosen from the VM's state alone (the record keeps only `agent_off`), and a record and state that disagree, as a choice changed while the VM ran leaves them, give none. Every other smolvm command devvm runs gets no `SSH_AUTH_SOCK`, and `machine exec` doesn't read it anyway (checked: an exec with your agent gives the VM none).
- **None is a path, not an agent:** `/dev/null` is a device, not a folder, so nothing, root included, can make a socket below it, and no process listens for it. An empty agent of devvm's would hold nothing too, but every VM set to none would share it: a VM could add a key there for another to use, lock it, or have devvm's process sign for keys it put in. With a path, there's nothing to add to, sign with, or share.
- **The lifeline check:** after each start, `Start` records the machine's lifeline (`agent.pid`: its process and start time) in the record (`started`; with network policy, `confined` too). `AgentUnchosen` (`backend.AgentStarter`, which Lima doesn't implement: its agent is the VM's config) says a running VM made forwarding may have an agent devvm didn't choose when the lifeline differs or its process is gone. A launch (devvm, `ssh`, `code`, after network policy's self-check, which says more for a VM with it) and an export's or `rm`'s start of a VM it finds running stop it then (`agent_unchosen_stop`, stopped even when interrupted), unless its choice is `on`: your agent is what it'd get anyway. The next devvm starts it as chosen.
- **The entry and devvm's connections follow the start,** as on every backend ([Docker's](#ssh-agent-forwarding-on-docker)): a choice changed while the VM runs reaches neither until its next start, as with smolvm's own agent. Here a start is told apart by its lifeline.
- **Only when allowed:** a VM made ready for it (`agent_toggle=on`) doesn't start once the toggle isn't let through (`Review.Allowed`, else the refusal), as with every port (it always is: it's reviewed). One made without forwarding (while the toggle wasn't let through) is refused when turned on (`agent_fixed`), before its state changes.

**What it relies on:** smolvm reading `SSH_AUTH_SOCK` only at `machine start` and keeping the path for that run, its host side connecting to that path and nothing else, whatever the VM sends; `machine exec` not starting a stopped machine (checked: it fails); the kernel refusing a path below a device; smolvm writing a new `agent.pid` at each start, which the VM can't write; devvm's state and records being on the host, out of the VM's reach (`~/.local/share/devvm`, never mounted).

**What could break it:** a smolvm release that reads the agent from somewhere else (its own config, the environment of a later command) or falls back to a default socket when the path fails (the off checks fail: they need the VM's agent to be unreachable, not empty); one that refuses a start whose path doesn't exist fails closed (the start fails). A devvm agent that ends while the VM runs leaves a VM set to `devvm` with no agent, never yours (smolvm connects to its path alone).

**Not covered:**

- **Starting the VM yourself, until devvm next looks:** `smolvm machine start --name devvm-…` from your shell (or any smolvm command of yours that starts it) gives a VM made with forwarding the agent your shell names, whatever its choice (checked), and it keeps it until devvm, `ssh`, `code`, an export or `rm` finds it running and stops it; `devvm ls`, a shell or editor you opened before, or nothing at all don't. Only you (or a program of yours on the host) can do it, not the VM.
- The VM has smolvm's agent socket while it runs, and an agent it's given is reachable for that whole time, not only while you're connected (smolvm's native forwarding, with `on` or `devvm`). With `devvm`, the VM can add keys of its own to devvm's agent, remove or lock its keys, as with any forwarded agent; every VM set to `devvm` shares it.
- Linux hosts are untested.

**End-to-end checks** (`tests/e2e.sh --backend smolvm`; your agent is a throwaway one of e2e's, devvm's has a throwaway key; every look into the VM is a `machine exec` run with your agent):

- every new VM is made forwarding, recorded, and given none (the mounts VM too, made from a shell without an agent);
- off, devvm run with your agent: root in the VM reaches no agent (`ssh-add -l` can't talk to one, rather than finding it empty) and can't add a key, your agent and devvm's unchanged; devvm's shell lists none;
- `devvm ssh-agent devvm` while it runs changes nothing until a restart, `ssh` by name after a launch included, then the VM and `ssh` by name list devvm's key alone; with devvm's agent ended, none, never yours; `on`, then yours alone, and root can add a key to it (the add check's control); `off` while it runs, stopped, then started by `devvm export` (no launch, its record still forwarding): none; `off` again after a restart, none; a VM made with `--ssh-agent`, turned off, none;
- stopped, then `smolvm machine start` from a shell with your agent gives it yours; `devvm export` then stops it in one line, writing nothing; started so again, devvm stops it too, and the next devvm starts it with none; `devvm ssh` on that start of devvm's keeps it running;
- with network policy, a VM started outside devvm with a decider of someone else's is still reported by the self-check (`net_unenforced_stop`) first.

### ssh for editors on Docker

**The guarantee:** as on Lima, ssh and editors reach a Docker VM by name, that VM alone (host keys of its own, read through `docker exec` and pinned), only as the VM's user and only with that VM's own key; an ssh session devvm's entry makes gives the VM no way out it doesn't already have, whatever the VM runs as sshd, as on [smolvm](#ssh-for-editors-on-smolvm); and nothing listens for ssh, in the container or on any network: the container publishes nothing, and other containers on its network reach no sshd. Reviewed, with [ports](#ports-on-docker) and the [agent](#ssh-agent-forwarding-on-docker), which share its transport: the threat check's leads are ruled out or listed below, and the end-to-end checks prove the rest.

**What it's built from:**

- **sshd in base,** as on smolvm (`sshd.sh`, `prepare.sh`'s locked password), in base's key.
- **Only when asked for:** `Confinement.SSH` at each start, when `Require` lets `ssh` through. `Start` then probes for `/usr/sbin/sshd` as root (an image without it starts without ssh, warned `vm_no_sshd`), makes the VM's key if it has none (`vmssh.EnsureKey`, shared with smolvm: `~/.local/share/devvm/docker/vms/<vm>.key`, mode 600, its public half the VM's only authorized key), and runs `services.sh` as root with `DEVVM_SSHD=inetd`: every host key deleted and a new ed25519 one made, devvm's sshd config written and checked (`sshd -t`), the same settings as smolvm's, and no daemon started. Then it reads the new host key's public half as root (`docker exec … cat`, at most 64 KiB, for 30 s) into a known hosts file of the VM's own (`<vm>.known_hosts`), which devvm's own sessions pin; a failure stops the VM.
- **No listener:** each connection runs `docker exec -i -u 0 <container ID> /usr/sbin/sshd -i -f /etc/devvm/ssh/sshd_config -E /var/log/devvm-sshd.log`: sshd in inetd mode, its standard input and output the connection (`docker exec` relays both, its stderr apart), one sshd per connection, ending with it. No socket in the container, no port published, no relay that parses anything: Docker's API carries the bytes.
- **`devvm _docker-connect`** (`docker.Connect`) runs it in devvm's place: with `-docker` (the path `Start`'s devvm found, so an editor whose `PATH` lacks it still reaches it), `-data` (devvm's data folder, the label value) and `-env` (only `DOCKER_HOST`, `DOCKER_CONTEXT` and `DOCKER_CONFIG`, as devvm had them: the same engine), it inspects the container by the VM's name and refuses one whose label isn't that data folder (`docker_container_foreign`), that isn't a VM's (`devvm.kind=vm`), or that isn't running (`vm_not_running`), then execs `docker exec` on the container's ID, never its name, so a container made by that name between the two isn't reached.
- **The entry:** `SSH` returns the VM's name as the host, no port, and that command as `SSHTarget.ProxyCommand`, which the shared ssh config writes in place of `ProxyCommand none` (one value, so a `Host *` of the user's can't replace it; checked with `ssh -G`). Its words are single-quoted, and a word with a quote, a backslash (fish reads those in single quotes), a `%` (ssh's tokens) or a control character is refused (`docker_ssh_path`); an entry with a newline isn't written. devvm's binary is named as it was run (`os.Executable`, a link kept: Homebrew's outlives the version it points to), and every launch writes the entry again.
- **Only for this start:** the record says the start ran its sshd (`ssh_up`, cleared before each start) and the container's start time then (`started`); `SSH` answers only while the container's `State.StartedAt` is that one. A container started outside devvm since (`docker start`, `docker restart`) gets no entry from devvm's next launch, and `devvm ssh` says so (`vm_no_ssh`); until then the entry written before still reaches it, with the config and host key devvm's start wrote and pinned (the container's disk keeps them).
- **devvm's shell** is an ssh session while `SSH` would answer (`ssh -F none -t`, the VM's key alone, the known hosts file above, `ControlMaster no`, the forwarder's options, the agent below), its command `cd -- DIR && exec bash -l`; otherwise `docker exec`.
- **Pinning** for the ssh config is the shared code's, as on the other backends: a VM's keys are forgotten before each start and read after it through `Exec` (`docker exec`, as the VM's user).

**What it relies on:** Docker's engine as the way into the container: whoever can run `docker` can exec into every container (root on a Linux engine's host), so the transport adds no one who couldn't already reach the VM; `docker exec` passing bytes unchanged both ways and closing sshd's input when ssh closes its own; container IDs being unique; OpenSSH's `sshd -i` (checked with Ubuntu's and Alpine's) and its client refusing unrequested channels; devvm's `Include` line first in `~/.ssh/config`; the user's shell running `ProxyCommand` (ssh uses `SHELL`).

**What could break it:** an editor that runs ssh without devvm's entry (none of devvm's options then); devvm's binary or `docker` moving after the entry was written (ssh fails to connect until the next launch writes it again: fails closed); a `DOCKER_HOST` that names another engine with a container of the same name and label (the label check passes only for this data folder's; the host key check refuses any other server).

**Not covered:**

- Root in the container chooses what `/usr/sbin/sshd` and its config are, as on smolvm: what keeps a session from carrying the VM out is the host's ssh. A remote forward you ask for (`ssh -R`) into a VM whose root allowed it isn't refused.
- Anyone who can run `docker` on the engine reaches the VM's sshd the same way, and the container itself; on Docker Desktop that's every program of yours.
- Sessions get `/etc/environment` and the variables `Start` names, as devvm's own commands do.
- `docker exec` runs as root in the container; the sshd it runs drops to the VM's user once the key is checked.
- What the container's sshd writes to its standard error reaches the terminal of the ssh that runs it (`docker exec` relays it, as `ProxyCommand`'s); a session's own output reaches it too. The port forwarder's goes to its log, limited.

**Threat check** (the security-audit skill, its local IPC companion; the three Docker emulations at once, as they share the transport). Leads, each confirmed or ruled out:

- **A `ProxyCommand` the VM shapes:** ruled out. Its words are devvm's binary, `docker`'s path, devvm's data folder and your Docker variables, none of them the VM's; each is single-quoted, one with a quote, a backslash, a `%` or a control character is refused, and an entry with a newline isn't written.
- **Another container reached:** ruled out. `devvm _docker-connect` takes only a container with this data folder's label and `devvm.kind=vm`, running, and execs on its ID; its name can't be a container ID's prefix (`devvm-` isn't hex); the pinned host key refuses any other sshd.
- **A host key read before this start's sshd config, or from another start:** ruled out. `SSH` answers only once `ssh_up` is set and while the container's start time is the one devvm's start recorded; keys are forgotten before each start.
- **A hostile sshd** (root replaces it or rewrites its config): what a session carries is the host's ssh's choice, so the entry's pinned options decide, as on smolvm; checked: no display and no key added through a `Host *` asking for them. `ssh -R` you ask for is then let through (Not covered).
- **The VM's bytes on your terminal through the connection's standard error:** ruled out as a new way: a session's own output reaches the same terminal; the forwarder's go to its log, limited, control characters shown as `?`.
- **An agent outside a session** (a socket mounted, Docker Desktop's `ssh-auth.sock`, `docker exec`'s environment, the forwarder's ssh): ruled out, checked.
- **An agent turned on for a running VM made without forwarding:** ruled out. devvm's shell and the ssh config's entry both follow the choice the VM's current start was made with, so it waits for the VM's next start, checked ([agent](#ssh-agent-forwarding-on-docker)).
- **A port the forwarder takes from the host, or from another VM:** ruled out, checked on both engines: a program's on `127.0.0.1` alone, `::1` alone, or every address, and another VM's listed port while it's free. On Linux the forwarder keeps `SO_REUSEADDR`, as Linux refuses the bind anyway while another socket listens on the port (checked by `internal/platform`'s tests, which run on Linux too).
- **A container started outside devvm:** ruled out. It gets no entry from devvm's next launch, its shell is a `docker exec` with no agent, and its forwarder ends once Docker reports another start.

**End-to-end checks** (`tests/e2e.sh --backend docker`, both engines):

- an entry by the folder's name with `devvm _docker-connect` as `ProxyCommand` and no port; the container publishes nothing (no port bindings) and nothing in it listens on port 22;
- the pinned host key is the VM's own, ed25519, its only one; a changed one is refused; a restart makes a new one, pinned again; another VM has its own, and its key doesn't log in to the first;
- `ssh` by name reaches the VM's user with `BASH_ENV`; agent forwarding stays off whatever `Host *` says; passwords and keyboard-interactive are refused, publickey alone offered; another key, `root` and another user are refused (devvm's key the control);
- remote forwarding (a port, a socket) is refused, a local forward works; `sshd -T` shows devvm's settings, and the config is root's alone;
- a hostile sshd (root rewrites its config to allow remote forwarding, X11 and tunnels), reached through a `Host *` that asks for X11 and to add keys to the agent: no display in the session and no key in the agent; the same asked for on the command line (`-Y`, `-o AddKeysToAgent=yes`) gets both (the controls), and `ssh -R` then works (what isn't covered); a restart writes devvm's config again, and `ssh -R` is refused;
- `devvm _docker-connect` refuses a container that isn't this devvm's (another data folder's label) and a stopped VM, in one line, exec'ing nothing;
- started outside devvm (`docker restart`), the VM has no entry, `devvm ssh` says so, and devvm's shell is a `docker exec`; `devvm restart` has ssh again;
- an image without sshd (root moved it away): the next start warns `vm_no_sshd` and runs without an entry;
- `devvm ssh`, `devvm code` (a stub `code`), `devvm stop` (no entry), `rm` (entry, key and pinned keys gone); an Alpine VM (`--from alpine:3`) reached the same way;
- `--clone`: the clone pushed in over ssh, every branch, nothing of the folder mounted, in a volume of its own; fetching the VM's commit and pushing a branch through devvm's ssh config; `rm -f` keeping the fetched work.

### Ports on Docker

**The guarantee:** the same as on [Lima](#ports-on-lima) and [smolvm](#ports-on-smolvm). When a VM forwards every port, each TCP port from 1024 up that a server in it listens on, on its loopback or on all its addresses, is forwarded to the same port on the host's loopback, and only to its loopback. When a VM lists its ports, only those are forwarded, however many it lists, with at most 256 at once as for every port. The forwarder never takes a port that a program on the host has on any address when the forward is made, or a port devvm records for another VM. Forwarding gives the VM no way out that it doesn't already have, because every connection starts on the host, and the container publishes nothing. The emulation is reviewed together with [ssh](#ssh-for-editors-on-docker), whose threat check covers it.

**What it's built from:**

- **The shared forwarder.** Docker's VMs use the forwarder that smolvm's VMs use (`vmssh.Forwarder`, `vmssh.Forwards`), and [its note](#ports-on-smolvm) says what it reads, how it listens and what its limits are. On Docker it runs as `devvm _docker-ports`, and `Start` starts it detached once the VM's sshd config is written and its host key pinned. The forwarder reaches the VM's sshd through `devvm _docker-connect`, which is its master's `ProxyCommand` and the same quoted command as the ssh config entry's, passed as `-proxy`. It logs in with the VM's key alone, checks the host key `Start` read, and forwards nothing either way.
- **Which ports.** The forwarder forwards every port from 1024 up when the record says `ports_all`, and otherwise the listed ports (`-only`). The listed ports are the record's less those `Confinement.Free` leaves out, which are the ports a program on the host has, as on every backend, with a `ports_taken` warning. A listed port below 1024 is also forwarded, because the user asked for it, and a bind the host refuses is logged. When no port is left, no forwarder runs. The forwarder never takes a port devvm records for a VM (`netpolicy.UsedPorts`), except the VM's own listed ones.
- **Its lifeline.** No host process runs a container, so the forwarder follows the container's start, which it gets as `-container` (the container's ID) and `-started` (its `State.StartedAt` after devvm's start). It asks Docker with `docker container inspect` by ID every 30 s, and whenever its connection ends. A stopped container ends that connection at once, because its `docker exec` ends. Once the container isn't running that start, the forwarder exits. `Stop` and `Delete` stop it first, and a start stops any forwarder the VM had before the container starts.
- **Set on any VM.** `SetPorts` changes the record. Nothing of Docker's changes, because nothing is published. On a running VM, it starts the forwarder again with the new ports, after stopping the old one, for the same start of the container and with the host key that start pinned. A container that isn't running the start devvm's record names, such as one started outside devvm, has no sshd of devvm's, so it gets no forwarder and devvm warns with `ports_no_ssh`.

**What keeps a forward from carrying the VM out:** the same as on smolvm. The master asks for no remote forward, agent, X11 or tunnel, and OpenSSH's client refuses a channel that the server opens unasked. Every connection starts on the host, and the VM's sshd opens it to the VM's own loopback.

**What it relies on:** the [ssh](#ssh-for-editors-on-docker) emulation's transport and pinned host key, and what the shared forwarder relies on, which is OpenSSH honoring `-F none` and the kernel refusing a bind without `SO_REUSEADDR` where another socket has the port. It also relies on Docker's container IDs and start times.

**What could break it:** a container restarted outside devvm keeps no forwarder, because the restart ends its connection and its start time differs. A `docker` that answers slowly delays the forwarder's check by at most 20 s per ask.

**Not covered:** the same as on [smolvm](#ports-on-smolvm). A VM can take a free port on the host's loopback that a program expects, host programs that bind all addresses later get their loopback connections sent to the VM, servers only on the VM's other addresses (such as its address on Docker's network) aren't forwarded, other users on the host reach the forwards, and UDP isn't forwarded. A VM without ssh, from an image without sshd, has nothing forwarded, and devvm warns with `ports_no_ssh`.

**End-to-end checks** (`tests/e2e.sh --backend docker`, both engines):

- With every port, servers on the VM's `127.0.0.1`, on `::1`, on all IPv4 addresses and on all addresses each answer at the host's `127.0.0.1`, and at `::1` where the host has it. The forwarder listens on the host's loopback alone. Its ssh master reads no config, offers the VM's key alone with its host key pinned, asks for no forwarding, and goes through `devvm _docker-connect`.
- A port that a host program has on every address stays the host program's, and a port below 1024 isn't forwarded. The host program also keeps its port when it's on the host's `127.0.0.1` alone, on its `::1` alone (so `localhost` never reaches two programs), or on `::`, which is IPv4 and IPv6 at once, where the host has IPv6. A server on the VM's own network address alone isn't forwarded, and neither is a port another VM's state lists while it's free, while a loopback server is forwarded as the control. A server that stops loses its forward.
- With listed ports, a listed port's server is forwarded and an unlisted one's isn't. A listed port that a host program has is left out with a warning, and forwarded again once it's free.
- On a running VM, a port that `devvm ports add` lists has its server reach the host at once, and once `devvm ports rm` takes it out, it doesn't. The container's start time is the same throughout, so it never restarted.
- The container publishes nothing. `devvm stop` stops the forwarder and closes its ports, a new start has a new forwarder, `docker stop` outside devvm ends it, and `rm` deletes it and its files.

### Ports on Lima

**The guarantee:** the same as on [Docker](#ports-on-docker). When a VM forwards every port, each TCP port from 1024 up that a server in it listens on, on its loopback or on all its addresses, is forwarded to the same port on the host's loopback, and only to its loopback. When a VM lists its ports, only those are forwarded. The forwarder never takes a port that a program on the host has on any address when the forward is made, or a port devvm records for another VM. Forwarding gives the VM no way out that it doesn't already have, because every connection starts on the host. Lima's own forwards listen with `SO_REUSEADDR`, so on macOS, whenever a server in the VM starts, Lima takes `127.0.0.1:PORT` while a program on the host has `*:PORT`, and that program's loopback connections go with it. That's why Lima forwards nothing and devvm's forwarder forwards by the same rules on every backend. On macOS, a VM with network policy doesn't depend on Lima for that, because its hostagent's sandbox refuses it every port but its ssh port, so Lima can't forward a port of the VM's even if it ignored its rules. The emulation is reviewed: the forwarder is the one reviewed for smolvm and Docker, and the parts that are Lima's own are below, with their threat check.

**What it's built from:**

- **Lima's forwards off.** Each VM's `portForwards` holds three ignore rules, each for every guest port and protocol (`any`, which is TCP and UDP). They're on `127.0.0.1`, which Lima also matches for `::1`, on `0.0.0.0` and on `::`, which together match servers on all addresses. They come ahead of Lima's own last rule, which forwards everything. `CreateVM` sets them with `limactl clone --set`. `Start` sets them only where `limactl list` shows other rules, because an edit gives the VM new host keys at its next boot. Lima's ssh is its VM driver's forward (`ssh.localPort`), not a rule, so the ignore rules leave it alone, and they cover the guest's own ssh port like any other.
- **The sandbox's binds (macOS, network policy).** The hostagent of a VM with network policy runs under a Seatbelt profile ([confinement](lima.md#confinement)) that denies every network bind but two kinds. It may bind the VM's ssh port over TCP, which devvm chooses and records in the VM's state (`ssh_port`), and unix sockets in the VM's Lima folder, which hold the hostagent's own socket (`ha.sock`), the VM's network (`default_ep.sock`, `default_fd.sock`) and ssh's control socket. Seatbelt matches a bind by its port alone, on any address, even when the rule names `localhost`, and it can't allow an ephemeral bind (port 0) without allowing every port. It matches a unix socket by its path with links resolved, so a link in the Lima folder doesn't let the hostagent bind a socket elsewhere. Lima's host resolver binds two ephemeral ports for its DNS server, so a VM with network policy starts with the resolver off and `127.0.0.1` as its DNS server, as on Linux, where nothing listens and lookups fail at once. The hostagent reaches the guest agent over vsock, which needs no bind. This list comes from starting a VM under a profile that reported every bind, then under one that denied the rest: Lima logs a forward it's refused (`failed to listen`) and carries on, while a refused resolver ends the start.
- **Which ports.** The backend keeps a record of which ports each VM forwards, `lima-vms/<vm>.ports`, holding `all`, `none` or a list. `CreateVM` writes it, and `SetPorts` writes it without editing Lima's config, then starts a running VM's forwarder again with the new ports. A VM without a record forwards nothing, and devvm warns with `ports_forward_failed`. When the VM lists ports, the forwarder forwards the record's less those `Confinement.Free` leaves out, which are the ports a program on the host has, with a `ports_taken` warning. When none is left, no forwarder runs.
- **The forwarder.** Lima's VMs use the forwarder that smolvm and Docker use (`vmssh.Forwarder`, `vmssh.Forwards`), and [smolvm's note](#ports-on-smolvm) says what it reads, how it listens and what its limits are. On Lima it runs as `devvm _lima-ports`. `Start` starts it detached once the VM runs, for project VMs alone, whose starts set `Confinement.HostKey` where builds' starts don't. The forwarder reaches the VM's sshd on Lima's ssh port on the host's loopback. It logs in as Lima's user with Lima's key, `_config/user` in devvm's Lima home, which every VM there authorizes. It never uses the user's agent, and it forwards nothing either way. The VM's sshd allows local forwarding alone (`base.sh`), and `-W` is local forwarding.
- **Reserved ports.** The forwarder never takes the VM's own Lima ssh port or its proxy port, which `Start` passes as `-reserve`. It also never takes the ssh, proxy and decider ports devvm chooses and records in any VM's state, or other VMs' listed ports (`netpolicy.UsedPorts`). Every Lima VM's ssh port is one of those, with or without network policy: devvm chooses it when it makes the VM, sets it with `limactl clone --set .ssh.localPort`, and records it as the VM's `ssh_port` before the clone (`Proxy.SSHPort`). devvm chooses a port while it holds a lock (`run/ports.lock`), so two devvm commands making or starting VMs at once never choose the same one. A stopped VM gets a new one only when a program on the host has its port on any address, even one that accepts no connections, or when the VM lists it to forward, and its start then sets it with an edit. Lima binds the port only once the VM boots, a few seconds after its start, so a port Lima picked itself would be free for another VM's forwarder in that window, and Lima's own ssh, which checks no host key, would then reach the other VM (the threat check below).
- **The host key.** devvm forgets a VM's pinned host keys before each start and reads them again after it, through `limactl shell`, at most 64 KiB for at most 30 s, into its `known_hosts` (`sshconfig.HostKey`). The forwarder gets the VM's ed25519 key from there, copied into its own known_hosts file and pinned with `HostKeyAlias` and `StrictHostKeyChecking yes`. The pin keeps the forwarder from talking to a program on the host that takes the ssh port. It doesn't guard against the VM itself, which is already the other end of the connection.
- **Its lifeline.** The forwarder follows the hostagent's pid file (`ha.pid`), as the proxy does, and exits once the file is gone or holds another pid. `Stop` and `Delete` stop it, and `Delete` also removes its files and the record.

**What keeps a forward from carrying the VM out:** the same as on smolvm. The master asks for no remote forward, agent, X11 or tunnel, and OpenSSH's client refuses a channel that the server opens unasked. Every connection starts on the host, and the VM's sshd opens it to the VM's own loopback. With network policy, the VM's own connections stay confined by Seatbelt or QEMU's `restrict=on`, while the forwarder runs on the host as devvm, outside the hostagent's sandbox.

**What it relies on:** what the shared forwarder relies on, which is OpenSSH honoring `-F none` and the kernel refusing a bind without `SO_REUSEADDR` where another socket has the port. It also relies on Lima binding its ssh forward on the host's loopback alone, on the host key that devvm pins at the start, and on Lima honoring the ignore rules ahead of its own rule. On macOS, a VM with network policy relies on Seatbelt refusing the hostagent's binds instead of on the rules, and on the Virtualization framework's own process, which runs outside the profile, binding nothing: the VM's network goes through the hostagent's unix sockets.

**What could break it:** a Lima release that forwards despite the ignore rules, or that forwards from somewhere other than `portForwards`. On macOS, a VM with network policy keeps the guarantee even then, because its sandbox refuses the binds. A VM without network policy, and every VM on Linux, where QEMU's `restrict=on` doesn't cover the hostagent's own binds, still relies on Lima honoring the rules. A Lima release that needs a new bind for a VM with network policy, such as a resolver that can't be turned off, fails its start closed, and Lima's log names the refused bind. The end-to-end checks look at the rules, and use `lsof` or `ss` to check that the hostagent has no TCP or UDP port of the VM's and that a host program keeps its port. A program on the host could take Lima's ssh port while the VM is stopped, and the pinned host key refuses it. Lima's key logs in to every VM in devvm's Lima home, as it does for Lima's own ssh, but public key authentication never sends the key to the VM.

**Threat check** (the security-audit skill, guidance mode, its local IPC companion; the sandbox's binds and the ssh port). Leads, each confirmed and fixed, ruled out, or listed:

- **Another VM answering for this one's ssh:** confirmed, fixed. An ssh port that Lima picks at a VM's start, and binds once the VM boots, is one devvm doesn't record, so no forwarder reserves it. Another VM forwarding every port, with a server on that port in the window, has its forward take it. Lima then carries on with its other ssh forward and waits on the port (seen with a host program holding it), and Lima's own ssh checks no host key (`StrictHostKeyChecking no`), so `limactl shell`, the host keys devvm reads and pins after the start, and devvm's setup and shell would reach the other VM. The fix: each VM's ssh port is devvm's, with or without network policy, recorded before the clone and reserved by every forwarder. It's unit-tested and checked by the CLI tests, and end to end, the port a VM's state records is the one Lima listens on.
- **A guest port bound around the rules:** ruled out on macOS with network policy. Lima forwards a port only by binding it on the host, and the sandbox refuses every port but the ssh port. End to end, with Lima's own rule put back for one start inside the sandbox, Lima tries the guest's TCP and UDP ports, is refused (`operation not permitted`), and has no port but its ssh port, while devvm's forwarder forwards the TCP port.
- **The ssh port on every address:** listed. Seatbelt allows the ssh port on any address, so a Lima that bound it on `0.0.0.0` would put the VM's sshd on the network, where it still takes only keys. Lima binds it on `127.0.0.1`, and the end-to-end checks look at the hostagent's listeners. The rule allows the port over TCP alone, so the guest's UDP server on that port number can't get a forward from it; checked end to end.
- **A program holding a stopped VM's ssh port:** ruled out, but for a race. A start looks for the recorded port with a bind on `127.0.0.1` and `::1` as well as a connection, so a program that has the port on any address, even one that accepts no connections, gives the VM a new port. Only a program that takes the port between that check and Lima's bind, a few seconds later, gets Lima's ssh, which is listed under not covered below. End to end, a VM whose port a host program holds starts on a new one, recorded, and the program keeps its own.
- **Two VMs choosing the same ssh port:** confirmed, fixed. Without a lock, two devvm commands making VMs at once could each choose the same port from the ports other VMs record, and the second VM's Lima would wait on a port that the first one's has. devvm chooses and records a port while it holds its ports lock.
- **A build VM's ssh port:** listed. A build's ssh port is the one Lima or the backend picks at its start, which no VM's state records, so another VM forwarding every port could take it in the window before Lima binds it. Lima's ssh would then run the build's scripts in that VM, which learns nothing secret from them, because builds carry no credentials. An image is the build VM's own disk, and a tool build writes its images through a folder that only its own VM mounts, so the other VM can break a build but can't choose what an image or a tool image holds.
- **What a failed start or create leaves:** ruled out. A VM whose create fails, other than by an interrupt, keeps its state, and with it its recorded port, until `devvm rm` deletes it, so the port stays reserved and nothing else takes it. `devvm rm` deletes the state, which frees the port.
- **Unix sockets:** ruled out as a way out. The hostagent binds them only in the VM's Lima folder, which only Lima's own commands and devvm use.
- **DNS around the proxy:** ruled out. With Lima's resolver off, the guest's DNS server is `127.0.0.1`, where nothing listens, and Lima's network's DNS address and the host's address on it answer nothing even when root asks them directly, because the sandbox denies the hostagent the host's DNS service and every connection but the proxy's; checked end to end.
- **A compromised hostagent:** listed. The bind rules stop a Lima that misbehaves, not code an attacker runs in it, which the profile still lets read and write your files.
- **Starts without the sandbox:** listed. Only network-policy starts on macOS run under it. A build keeps Lima's host resolver, so its binds aren't denied, and a VM without network policy starts unconfined. Such a VM could run under a profile that denies binds alone, as its ssh port is fixed, but it would need Lima's resolver off too, which changes how it resolves names (the user-mode network's own DNS instead of the host's resolver), so that's proposed rather than done.

**Not covered:**

- Everything on [smolvm's list](#ports-on-smolvm) applies. A VM can take a free port on the host's loopback that a program expects, host programs that bind all addresses later get their loopback connections sent to the VM, servers only on the VM's other addresses aren't forwarded, other users on the host reach the forwards, and UDP isn't forwarded.
- Another user on the host can take a VM's ssh port while the VM is stopped or booting. Lima's own ssh would then reach that user's program, as it checks no host key, while devvm's forwarder and ssh config pin the VM's.
- A VM started outside devvm, such as with `devvm limactl start`, or one whose forwarder ended, runs without forwarded ports until its next start through devvm, or until `devvm ports` changes its ports, which starts a forwarder with the host key devvm pinned at its last start.

**End-to-end checks** (`tests/e2e.sh`, `project`, and `network` for the sandbox's binds):

- Lima's rules ignore everything, the forwarder runs with the host key devvm pinned for the VM, and Lima's ssh listens on the port the VM's state records.
- A stopped VM whose ssh port a host program holds, on `127.0.0.1` alone and accepting no connections, starts on a new port that its state records, and the program keeps its own.
- A VM server on a port answers at the host's `127.0.0.1` through the forwarder, while Lima's hostagent has neither that port nor a UDP server's port. The forward listens on the host's loopback alone. A port that a host program has on every address keeps that program's `localhost` connections while a server in the VM listens on it, and the forwarder logs that port as not forwarded.
- With listed ports, only those reach the host, whatever address the VM's server is on. A listed port that a host program has is left out with a warning, and forwarded again once it's free.
- On a running VM, `devvm ports` changes the forwarder's ports at once. A port that `devvm ports add` lists has its server reach the host at once, and once `devvm ports rm` takes it out, it doesn't. The VM's boot ID is the same throughout, so it never restarted.
- `devvm stop` stops the forwarder, `limactl stop` outside devvm ends it (on macOS), and `rm` deletes its files and the record.
- On macOS, a VM with network policy has a profile that denies every bind but its ssh port's over TCP and unix sockets in its Lima folder, and the same binds that work outside the profile, a TCP port and a UDP socket on the ssh port, fail under it. Its hostagent listens on its ssh port alone, with Lima's resolver off. Started again with Lima's own forwarding rule put back inside the sandbox, the hostagent tries a VM server's TCP and UDP ports and is refused, and has neither. The VM still works: ssh by name, devvm's forwarder (on the host's loopback alone), the proxy and the self-check. Its next start puts the ignore rules back.
- With network policy, DNS fails at once, and Lima's network's DNS address and the host's address on it give no answer for a name.

### SSH agent forwarding on Docker

**The guarantee:** as on Lima, a VM gets an SSH agent only in ssh sessions that forward one, and every session devvm makes or describes forwards only the agent the VM's choice names: with `devvm`, devvm's own and never yours; with `off`, none. No agent socket is mounted into a container, so a program in the VM reaches an agent only while such a session is open. A change applies from the VM's next start, in devvm's shell and the ssh config's entry alike. Both `agent-forwarding` and `agent-toggle`, reviewed with [ssh](#ssh-for-editors-on-docker) (its threat check).

**What it's built from:**

- **Nothing at create:** forwarding is the sessions', not the container's, so it's a flag in the record (`forwarding`), set when the VM is made (`--ssh-agent`) and by `SetAgentForwarding` on a stopped VM; `Inspect` reports it, and never `AgentFixed`.
- **The start's choice:** `Start` records whether its sessions forward an agent (`agent`): none when the record says off or the start's `Confinement.NoAgent` does (either is enough), else `vmssh.AgentUser`.
- **The choice each start was made with** (shared code, every backend): devvm records it in the VM's state with each start it makes (`ssh_agent_started`: the choice and a hash of the backend's `StartID`, which differs for every start, devvm's or not: Lima's hostagent pid file by its pid and when it was written, smolvm's lifeline, the container's ID and `State.StartedAt` here). A running VM whose start matches runs with that choice; a stopped one, or one started outside devvm, with its current choice.
- **devvm's shell** then has `ForwardAgent yes` with `IdentityAgent SSH_AUTH_SOCK`: the shell gets devvm's environment, whose `SSH_AUTH_SOCK` every launch sets from the choice the VM runs with (devvm's own socket, yours, or none: unset), as Lima's does; otherwise `ForwardAgent no` and `IdentityAgent none`.
- **The ssh config's entry** forwards the choice the VM runs with too, as for Lima (shared code): `ForwardAgent` per mode, devvm's socket as `IdentityAgent` too. `devvm code` gets devvm's own environment, your `SSH_AUTH_SOCK`, and the entry decides.
- **Every other way in forwards none:** `docker exec` (devvm's setup, `Exec`, the shell without ssh) passes only the variables devvm gives it, never `SSH_AUTH_SOCK`; the port forwarder's ssh has `ForwardAgent no` and `IdentityAgent none`. A container started outside devvm runs no session of devvm's: its shell is a `docker exec`, its entry gone.

**What it relies on:** OpenSSH's client forwarding only the agent `ForwardAgent` and `IdentityAgent` name, and only when asked; devvm's `Include` line first in `~/.ssh/config`; `docker exec` not forwarding an agent of its own (Docker Desktop's `/run/host-services/ssh-auth.sock` is mounted only when asked, and devvm never asks).

**What could break it:** an entry stays as devvm's last launch wrote it, as on Lima: a VM stopped and started again outside devvm keeps the entry of its last start until devvm's next launch writes it again.

**Not covered:**

- While a session forwards an agent, root in the VM can use it (its socket is in the session's `/tmp`), as on Lima; with `devvm`, it can add keys to devvm's agent, remove or lock them.
- An agent you forward yourself (`ssh -A`, a `ForwardAgent` of yours for another host name).

**End-to-end checks** (`tests/e2e.sh --backend docker`, both engines; your agent is a throwaway one of e2e's, devvm's has a throwaway key):

- no socket is mounted into the container; `docker exec` as root finds no agent;
- off: devvm's shell lists no agent, and `ssh` by name forwards none whatever `Host *` says;
- `devvm ssh-agent devvm` while it runs: the next shell and `ssh` by name still list your key alone; after a restart, devvm's key alone, never yours; `on`, then yours alone; `off` again, none;
- a VM made with `--ssh-agent`: the shell lists your key; turned off, none;
- a VM made without it: the shell lists none; turned on while it runs, the shell and `ssh` by name still none after devvm's next launch; after a restart, both yours.

### Network policy on Docker

**The guarantee:** as on Lima, a Docker VM with network policy reaches nothing but its own proxy, even as root, on Docker Desktop and on an engine of this Linux machine: no other address, IPv4 or IPv6, no name resolved outside and no DNS query leaving its network, not the host's services on its loopback or any address. The proxy, devvm's CA and the VM's tokens never enter Docker: they stay host processes and files, as on the other backends. A start devvm didn't make confined, or a VM given another way out since, is `unenforced`, and devvm stops it. Reviewed, with [build confinement on Docker Desktop](#build-confinement-on-docker-desktop), which uses its parts: the threat check's leads are fixed, ruled out or listed below, and the end-to-end checks prove the rest, on both engines.

**Why the proxy stays on the host:** it reads tokens from the macOS Keychain (`devvm secret get`), refreshes Codex's and opencode's OAuth logins in the user's own login files, and holds devvm's CA key, which can impersonate any site to every VM. A proxy in a container would need the Keychain's values, the login files and the CA key inside Docker (on Docker Desktop, a VM every container shares), or another way back to the host for each. On the host, tokens, the Keychain, the CA key and login refresh never enter Docker. The one path from the host into the relay is the proxy's unix socket, mounted into the relay alone; the relay is the VM's one way to the proxy, and it reads nothing it carries.

**What it's built from** (`internal/backend/docker/egress.go`; the proxy is the shared one, `netpolicy.Proxy`):

- **A network of the VM's own,** `<vm>-net`, labelled: `--internal` (no route out; Docker's resolver answers only members' names, and forwards no other query) and `com.docker.network.bridge.inhibit_ipv4=true` (no address of the host's on the bridge: without it, on Linux, the gateway reaches the host's servers on every address). No IPv6 on it (`EnableIPv6` false). One that's someone else's by that name is refused; one of devvm's that doesn't confine is made again. Before each start through the proxy, with the old relay deleted, a network with any container on it is refused, naming it (`docker_network_shared`), before the VM starts; so is deleting one (network off, `rm`) that a container devvm didn't put there still runs on.
- **The VM on it alone:** before each start through the proxy, `docker network disconnect` from every other network and `connect` to its own, on the stopped container; the container was made on Docker's default network, and its config hash doesn't include the network, so turning network policy on or off never makes it again. The VM gets no capability, `--privileged` or device added.
- **No `NET_RAW`:** every Docker VM's container is made with `--cap-drop NET_RAW`, which is in its config hash, so a container that has `NET_RAW` is made again without it (`docker_remaking`) at its next start. NET_RAW isn't in its bounding set, so even root opens no raw or packet (`AF_PACKET`) socket: nothing it sends gets past its kernel's IPv6 being off, or forges frames on the bridge. `ping` works through ICMP datagram sockets, which Docker allows every group (`net.ipv4.ping_group_range` `0 2147483647` in containers not on the host's network); iputils' `ping` from Ubuntu's packages runs as the VM's user.
- **IPv6:** the network has none (`EnableIPv6` false). **The container:** Docker turns IPv6 off on its interface (`disable_ipv6` 1 on `eth0`), so its only IPv6 address is `::1` on its loopback; any other interface with IPv6 on (a kernel's fallback tunnel devices, such as `sit0`, where it makes them) is down with no address. Root in the VM can change none of it: `/proc/sys` is read-only in the container, and bringing a device up or adding an address needs `NET_ADMIN`. **The bridge's host side** (`br-<id>` on the engine): IPv6 on (`disable_ipv6` 0) with one address, link-local (`fe80::`), and no other (checked on both engines; for one run, `fe80::1445:82ff:fe2e:9f72` on the Linux engine and `fe80::24e3:a5ff:fe7a:ab88` on Docker Desktop, `disable_ipv6` 0 on both). **Why the VM can't use it:** its kernel neither sends nor takes IPv6 on `eth0`, so no socket of its reaches that address, and without `NET_RAW` it has no packet socket to put an IPv6 frame on the bridge past its kernel.
- **The relay,** `<vm>-proxy`, made again at each start: `docker container create` from `devvm-<hash>:proxy`, an image devvm imports from an empty tar archive (nothing downloaded, nothing in it), with devvm's own Linux build mounted read-only at `/devvm` as its entrypoint, `_proxy -relay 0.0.0.0:<port> -relay-to /run/devvm/proxy.sock`; `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pids-limit 64`, 128 MiB, no port published, on the VM's network alone with the alias `devvm-proxy`; its container's ID, from `docker container inspect` once it's made, is what's started and what the record keeps (`relay_id`). It accepts TCP on any address of its own and copies bytes, unread, to a new connection to the socket for each; it never dials anything else (`internal/proxy/relay.go`).
- **The proxy's socket:** the host proxy also listens on a unix socket (`-listen-unix`, mode 600, in a folder of the VM's own, mode 700, under `~/.local/share/devvm/docker/sock/`, named by a hash of the VM's name), which `netpolicy.Prepare` asks for when the backend implements `backend.ProxySocket`. Mounted into the relay alone: on Docker Desktop the socket itself (`-v`: `--mount` refuses a socket there; Desktop connects by its path at each connection, so a proxy started again is reached; it shows the socket as root's 0660, so the relay runs as `0:0`, its capabilities dropped); on Linux its folder, read-only (a socket mounted alone stays the inode that was there), the relay running as the host's user. The proxy then checks the VM's password and policy on each connection as on any backend; the relay is just another client of the socket.
- **The VM's proxy settings:** `ProxyURL` is `http://devvm:<password>@devvm-proxy:<port>`; at each start, `HTTP_PROXY`, `HTTPS_PROXY` (and lowercase) and `Confinement.Env` go into a block of the container's `/etc/environment` (`envScript`, fed on `docker exec -i`'s input as root, never in an argument; values limited to URL-safe characters), which devvm's `docker exec`s (`loginEnv`), sshd's sessions (`services.sh`'s `SetEnv`) and the setup read; a start without network policy empties the block. The container's own environment (`docker create -e`) holds none of it, so none of it is in `docker inspect` either. There, every proxy variable is set empty (`noClientProxy`), so the proxies in the Docker client's `~/.docker/config.json` don't go in ([a company proxy](#a-company-proxy)).
- **The lifeline:** after the start, `docker container wait <ID>` runs detached on the host (`Detach`), its pid in `<vm>.lifeline` beside the VM's record; the proxy follows that pid, so it exits when the container stops or Docker's engine goes away. The file is removed before each start.
- **Confined** compares the record's `confined` (the container's ID and start time when devvm's start through the proxy finished), `net_id` and `relay_id` with Docker's: the same start, running, on its own network alone (by ID), that network still internal with `inhibit_ipv4`, labelled, and with no member but the VM's container and the relay that start made, both by ID (a container named as the relay isn't it). `docker start`, `docker restart`, `docker network connect`, another container put on the network or the relay replaced, or the network made again all make the VM `unenforced`; its next launch stops it, and the one after refuses a network with someone else's container on it.
- **On and off:** `devvm network` applies at the next start, which moves the container between its own network and Docker's default one; off, the relay, its network and the block go.

**What it relies on:** Docker's bridge driver enforcing `--internal` (iptables/nftables rules on the engine's host: Desktop's VM, or this Linux machine) and `inhibit_ipv4`; Docker's embedded resolver not forwarding queries from an internal network (CVE-2024-29018, fixed in Docker 26.0.0, 25.0.5 and 23.0.11; devvm needs 29.1); Docker turning IPv6 off on a container's interface on a network without it, keeping `/proc/sys` read-only and dropping the capabilities asked for; Docker Desktop's socket forwarding connecting only by the path, at each connection, and only for containers given the socket; the relay's code passing bytes and dialing nothing but its socket; the engine's container isolation for everything (a container is not a VM). Linux engines rootful, on this machine (`kindLinux`), and Docker Desktop: other engines can't mount a socket of this machine's, so they have none of it.

**What could break it:** a Docker or Desktop release that lets an internal network route out, gives the host an address on it despite `inhibit_ipv4`, or forwards its DNS (each fails the end-to-end checks); someone with Docker access changing the network or the VM's networks while it runs (devvm sees it at its next launch, `unenforced`, and stops it; until then it reaches what they gave it); a program of the user's that binds the socket's path while the proxy is down (only the user can: the folder is theirs alone, 0700; the relay then reaches that program); root in the VM killing or rewriting nothing outside it: the relay is another container, and the VM can't reach the socket.

**Not covered:**

- Anyone who can run `docker` can attach the VM to any network, or run a container on its network that routes out, as on smolvm someone on the host can widen an allow list; devvm notices at the VM's next launch, not while it runs.
- Containers on Docker Desktop all run in one VM: a kernel or Docker flaw there reaches past every network.
- What the container's own loopback holds: servers the VM runs on it are its own, and the port forwarder reaches them over ssh, as without network policy.
- The relay accepts connections from anything on the VM's network; only the VM and itself are on it, and every connection still needs the VM's password at the proxy.
- Tools that need raw or packet sockets (`tcpdump`, `arping`, raw `nmap` scans) don't run in Docker VMs, with network policy or without.
- Docker Desktop's DNS capture runs in the network namespace a host-network container gets (Desktop's VM's, where its bridges, `eth0` and Docker's resolver's forwarding are); a query that left through some other path of Desktop's (its own processes outside that namespace) wouldn't be seen. The control is a lookup from Docker's default network, which the capture does see leave.
- The proxy's own limits ([Not covered](../safety/network.md#not-covered)).

**Threat check** (the security-audit skill, its local IPC and data isolation companions; with [build confinement on Docker Desktop](#build-confinement-on-docker-desktop)). Leads, each confirmed and fixed, or ruled out:

- **A container by the relay's name standing in for it** (one that routes out, put there by someone with Docker access, with the VM still `confined`): confirmed, fixed: the relay's container ID is recorded when devvm makes it, it's started by that ID, and the network's members are checked by ID; checked: a container made by the relay's name on the network makes the VM `unenforced`, its next launch stops it, and the one after starts it confined with a relay of devvm's.
- **Someone else's container left on the VM's network** (each start failing closed, with nothing saying why): confirmed, fixed: such a network is refused before the VM starts, and when devvm would delete it, in one line naming the network and what to do (`docker_network_shared`); checked (deleting it: unit-tested): refused, the VM not started, then started once that container is gone.
- **Raw and packet sockets** (frames past the VM's kernel, IPv6 to the bridge's link-local address, spoofing on its network): confirmed, fixed: every VM's container (and Desktop's builds') is made without `NET_RAW`; checked: not in the bounding set, root opens neither socket, `ping` still works.
- **IPv6:** ruled out, checked on both engines: `disable_ipv6` 1 on the VM's interface, its other IPv6 interfaces down, `::1` its only address, `/proc/sys` read-only; the bridge's engine side has a link-local address alone, which the VM could reach only with a packet socket, which it can't open.
- **DNS forwarded from the internal network** (CVE-2024-29018's way out): ruled out, checked on both engines with a capture on the engine's own network: none of the probe's queries (its resolver, `127.0.0.11`, `1.1.1.1` and `8.8.8.8`, UDP and TCP, A, TXT, ANY, AAAA, HTTPS, EDNS0) left; a lookup from the default network did (the control). Docker 29.1 is past the fix; on Docker Desktop the capture's reach has a limit (Not covered), past which Desktop rests on that fix.
- **A build's proxy stopped by a pid another process has since** (`SIGTERM` to whatever has it): confirmed, fixed: the backend keeps the `*os.Process` it started the proxy as (`platform.StartDetachedProcess`), never waits for it, and `buildNet`'s cleanup signals through it (`BuildProxy.Stop`): the pid stays that process's while devvm hasn't waited for it (on Linux Go signals through a pidfd), so no other process can be given it; unit-tested: a running one ends by `SIGTERM`, one already waited for is refused as done.
- **A unix-socket client trusted for its address:** ruled out. The proxy reads no peer address; the socket's clients get the password and policy checks of any other.
- **The relay reaching anything but its socket:** ruled out. It dials only `-relay-to` (`relay.go`), runs read-only with no capabilities, `no-new-privileges`, 64 processes and 128 MiB; at most 512 connections at once, more wait.
- **The socket reached by others:** ruled out. Its folder is 0700 and the socket 0600, the user's; mounted into the relay alone, never the VM.
- **The socket reached through a VM's own mounts** (a project folder holding devvm's data folder): ruled out. A project folder can't be, hold or be inside devvm's data folder (`project.Unsafe`), agents' folders are their own, and Docker Desktop connects no socket inside a mounted folder.
- **The proxy's password through `/etc/environment`:** ruled out. Names and values are checked (URL-safe characters) and fed on `docker exec`'s input, never in an argument or the container's environment; checked: in no host process's arguments, nor the relay's.
- **devvm's Linux build replaced on the way:** ruled out. `linux.go` checks the SHA-256 of a fetched build before it's used; the tar entry's name only picks the regular file `devvm` (at the top or in one folder), written to a path of devvm's own; it reads at most 256 MiB; then Go's build info must match.
- **A build's proxy settings left in its image:** ruled out. The env file is 600; `/etc/sudoers.d/devvm-build-proxy` is removed before the commit.
- **The lifeline's pid file from an earlier start** (the proxy following a stopped container's wait): ruled out. The file is removed before each start; a pid file written since the proxy started whose process is already gone ends it, an older one is waited past.

**End-to-end checks** (`tests/e2e.sh --backend docker`, both engines):

- the VM on its own network alone, internal, `inhibit_ipv4`, without IPv6, labelled, its members by ID the VM and the relay its record names; the relay devvm's Linux build in the empty image, read-only, no capabilities, `no-new-privileges`, nothing published, two mounts; the VM with no capability added, `NET_RAW` dropped and out of its bounding set, root opening no raw or packet socket;
- the proxy's password in no host process's arguments while devvm launched it, nor in the relay's arguments or environment; the VM's proxy settings have it;
- an allowed host works through the proxy; another gets `403`, and so does the host's loopback through the proxy;
- direct connections fail even as root: an address, IPv6, a name, the host's servers on its loopback and on every address (through the default network's gateway on Linux, Desktop's host address and name on Desktop); the relay answers `407` without the password;
- no name resolves, even as root (the relay's does); no DNS query leaves the network: a capture of port 53 on every interface of the engine's network namespace (on the docker host VM; on Desktop, from a container of the sandbox's on Desktop's host network) sees none of the probe's names, while it sees the same VM's lookup leave once it's on the default network (the control);
- IPv6: off on the VM's interface, its other interfaces down, `::1` its only address, `/proc/sys` read-only; the bridge's engine side with no IPv6 address but link-local ones, recorded;
- `devvm log` shows the block; `devvm policy allow` and `rm` apply at once;
- a token bound to it: the VM gets its own placeholder, never the token, nor does its relay; the proxy puts it in; unbound and deleted at once;
- with its proxy killed, nothing gets out; launched, it gets a new proxy on the same socket, which the same relay reaches;
- connected to Docker's default network while it runs: `unenforced`, and its next launch stops it and opens nothing; then started confined again, the extra network gone;
- its relay replaced by a container of the same name on its network: `unenforced`, stopped at its next launch, confined again at the one after;
- `docker stop` outside devvm: the proxy exits; `docker start` outside devvm: `unenforced`, stopped at its next launch;
- another container on its network: the next launch refused in one line naming the network, the VM not started; started once it's gone;
- `devvm stop` stops the VM, relay and proxy; `devvm network off` starts it on the default network alone, without relay, network, proxy or settings, where the direct probes get out and the capture sees its lookup leave (their controls), and iputils' `ping` works as the VM's user; `on` confines it again; `rm` deletes it, its relay and network, and its proxy exits.

### Build confinement on Docker Desktop

**The guarantee:** as on Lima, a build on Docker Desktop (an image's, or the shared tools') reaches the internet but not the host's services, on its loopback or elsewhere, nor anything internal; a build with no network (`NetNone`) reaches nothing. Desktop's default network reaches the Mac's loopback (`host.docker.internal`), so builds don't use it. Reviewed with [network policy on Docker](#network-policy-on-docker) (its threat check).

**What it's built from:** network policy's parts, for the build alone (`buildNet`): its own internal network with `inhibit_ipv4` (refused with another container on it, `docker_network_shared`) and its relay, the build's container made without `NET_RAW` (`buildCaps`), as a VM's, and a proxy of devvm's on the host, started by the backend itself (`backend.ProxyStarter`, which Lima's builds behind a company proxy use too: `devvm _proxy` with `-listen 127.0.0.1:0`, `-listen-unix`, a random password in a file, a policy file of `**`, any host on ports 80 and 443, and the proxy's floor refusing the host's own and internal addresses, and `-lifeline` on `docker container wait` of the build's container). The build's commands get the proxy's address from an env file (`docker exec --env-file`, mode 600), never their arguments; while the scripts run, `/etc/sudoers.d/devvm-build-proxy` keeps it for `sudo`, and it's deleted before the commit, so nothing of it goes into the image. When the build ends (or fails, or is interrupted: a cleanup), the proxy is stopped (through the process devvm started, never by a pid alone) and the relay and network deleted; a failed build's container, kept for inspection, is taken off the network, and its proxy's logs kept beside it.

**What it relies on:** what network policy does, and the build's tools honouring the proxy variables (apt, apk, curl, git, mise, npm and the tools' installers do); a tool that resolves names itself or connects without them fails, as names don't resolve on the network.

**Not covered** (known limits, to revisit):

- **Which hosts a build reaches:** any host on ports 80 and 443 (`**`), not an allowlist. `base.policy` and each layer's policy would need every host a build fetches from listed (base's package snapshot, `snapshot.ubuntu.com`, isn't in `base.policy`; a layer of the user's names whatever it downloads), and builds on the other backends reach the whole internet, so an allowlist here would make Desktop builds fail where theirs work. A build's script can send data to any public host on those ports.
- **Other ports:** a build reaches none (git over ssh, other protocols), where other backends' builds do.

**End-to-end checks** (`tests/e2e.sh --backend docker`, Desktop):

- `devvm doctor` shows `build-confinement` and `egress-proxy` `emulated`, and finds devvm's Linux build;
- base built, its proxy, relay and network gone afterwards;
- a layer reaches the internet through the proxy and not the Mac's loopback: not directly (Desktop's host address, `host.docker.internal`), not through the proxy (`127.0.0.1`), and no name resolves; `NET_RAW` isn't in its bounding set;
- the shared tools, a node VM's layer and an Alpine base (`--from alpine:3`) built the same way.

### The docker layer on Docker

**The guarantee:** a Docker VM runs Docker's engine inside without `--privileged`, on any engine: under Sysbox, on a Linux engine of this machine's that has it, root in it is root of a user namespace of its own, and it reaches no other container (the user's included, on Docker's default network or any other) and not this machine's loopback, even as root; it gets no network policy, at any step. Anywhere else the layer is refused in one line, before anything changes. Reviewed: the threat check's leads are fixed, ruled out or listed below, and the end-to-end checks prove the rest, on a Linux engine with Sysbox (the refusal on Docker Desktop).

**The problem:** Docker's engine in a container needs more than devvm gives its other containers: `NET_ADMIN` for its bridge and iptables, mounts for its storage, writable cgroups and `/proc/sys`. Dev Containers' docker-in-docker runs the container `--privileged`, with volumes for `/var/lib/docker` and `/var/lib/containerd` and an entrypoint that starts `dockerd`. devvm doesn't offer `--privileged` at all: it gives root in the VM every capability, every host device, no seccomp, no AppArmor, and writable `/sys` and cgroups, so it can load kernel modules, write the engine's disks and leave the container; on Linux that's, in effect, root on the host, and on Docker Desktop root of Desktop's VM, with every container in it and every folder Desktop shares (by default `/Users`). So the layer runs under Sysbox, on a Linux engine of this machine's that has it, and elsewhere is refused in one line pointing to a VM backend (`docker_layer_no_sysbox` on a Linux engine of this machine's, `docker_layer_needs_vm` elsewhere).

**How it's kept:**

- **Root in the VM is root of its own user namespace:** its uid 0 is an unprivileged uid range on the host (`/proc/self/uid_map` is `0 100000 65536`, not the identity), and Sysbox emulates `/proc` and `/sys` so that `dockerd` runs without `--privileged`. It has every capability in its own namespaces (the bounding set full: `NET_ADMIN`, `NET_RAW`, `SYS_ADMIN`), and its network namespace's `/proc/sys` is writable. Its mounts are ID-mapped: the user's files are the user's in it, and what root writes there is the host's root's, as in any Docker VM (Not covered). Everything else a Docker VM keeps (only the project folder mounted, agents' folders read-only, Docker's seccomp profile, no devices) holds as for any container, as far as Sysbox's own code holds.
- **It reaches no other container:** it's on a network of its own (`<vm>-docker-net`: labelled, a plain bridge, not internal, so it reaches the internet), made before the container names it (Docker would make one unlabelled), in the container's config hash, with nothing else on it: a start finding another container on it is refused (`docker_network_shared`), and so is deleting the VM, before anything's deleted (`checkAlone`, then `removeNetwork` as for network policy's networks). One of devvm's by that name that isn't a plain bridge (internal, IPv6, any option such as another gateway mode) is made again. With `NET_RAW` and `NET_ADMIN`, root in it can send anything on its own bridge, and nothing else is there but the engine's host; the engine's rules between bridges (`DOCKER-FORWARD`, by interface, whatever addresses a packet carries) keep it from every other network's containers.
- **Not this machine's loopback, even routed to:** root can route `127.0.0.1` to its gateway in its own namespace (`route_localnet` on, the local table moved behind its own rule) and so put packets for the host's loopback on the bridge; the engine's host drops them as martians, as the bridge has `route_localnet` off (Docker's default, with its userland proxy on). devvm reads it (`/proc/sys/net/ipv4/conf/br-<id>/route_localnet`, the network's ID's first 12 characters) each time it readies the network, at creation and each start, and refuses the VM in one line when it's on or can't be read (`docker_route_localnet`, `docker_bridge_unreadable`). That's why the layer runs only on a Linux engine of this machine's (`kindLinux`): another machine's bridges can't be read.
- **No network policy**, at any step: `plan` doesn't ask, whether the layer was named or a devcontainer.json's docker-in-docker asked for it: it makes the VM without network policy and warns (`net_off_docker_layer`), and refuses `--network-policy` (`net_docker_layer`); `devvm network on` refuses it, adding the layer in place to a VM with network policy is refused before anything changes, a launch whose state says `net=on` (edited by hand) refuses to start it, and the backend's `Start` refuses `NetProxy` for a VM whose record is made for the layer. So nothing claims to confine a VM that can change its own network.
- **The same in place, and as it was when that fails:** the layer added to a VM (`SetDockerLayer` on, on the stopped VM, recorded as `docker_layer=sysbox`) makes its next start make the container again from a commit (the remake that agents' folders use), with the runtime, its own network and its engine's volumes, its disk and home kept. When a script of the layers added fails (or is interrupted), the VM is stopped and made as it was (`SetDockerLayer` off): its container made again at once from a commit on Docker's runtime and default network, without `NET_RAW`, its own network and engine's volumes deleted, `docker_layer` emptied, its image set back; network policy can be turned on again.

**What it's built from:** `VMSpec.DockerLayer`, `backend.DockerLayerVM` (`DockerLayer`: the runtime or the refusal; `SetDockerLayer`, on or off); the backend's record (`Runtime`) and its container config, which the config hash covers: `--runtime sysbox-runc`, its own network, no `--cap-drop` (Sysbox gives root every capability in its namespace unless it's told to honour them, `SYSBOX_HONOR_CAPS`, and then `dockerd` can't make its iptables chains), and volumes of the VM's own for `/var/lib/docker` and `/var/lib/containerd` (labelled, made before the container names them, deleted with it, kept when the container is made again). `services.sh` starts `dockerd` after each start for such a VM (`DEVVM_DOCKERD` unset), and only counts a pid file whose process is `dockerd`: a pid file an image kept from its build isn't another process's. `DEVVM_LOOP=off` skips the loop devices for every Docker VM (its tools are folders), which Sysbox's user namespace can't make. Sysbox is detected from `docker info`'s runtimes (`sysbox-runc`), and `devvm doctor` says so (`docker_sysbox`).

**What it relies on:** under Sysbox, the kernel's user namespaces and ID-mapped mounts, and Sysbox's emulation of `/proc` and `/sys` (`sysbox-fs`, a FUSE file system); Sysbox runs only on Linux engines, and on Ubuntu 25.04 and later needs fusermount3's AppArmor profile widened for `/var/lib/sysboxfs` ([details](../backends/docker.md#the-docker-layer)); Docker's rules isolating bridge networks from each other; `route_localnet` off on the VM's bridge on the engine's host, read where Docker names it (`br-` and the network's ID's first 12 characters, for a network without a bridge name of its own: devvm's are plain).

**What could break it:** `route_localnet` turned on for the VM's bridge while it runs (by someone root on the engine's host; devvm sees it at the next start, and refuses it); an engine or firewall that lets bridges reach each other; someone with Docker access putting another container on the VM's network while it runs (devvm sees it at the next start, and refuses it).

**Not covered:**

- **Network policy.** Root in the VM controls its own network namespace: it can add routes (`NET_ADMIN`), and turn IPv6 on for its interface (`/proc/sys` is writable under Sysbox), then reach the host's servers on `::` through the bridge's link-local address (checked by hand on network policy's internal network with `inhibit_ipv4` too, with `NET_ADMIN` and `NET_RAW` dropped and `SYSBOX_HONOR_CAPS` set: `/proc/sys` stays writable). So network policy's guarantee can't hold, and it's refused, not emulated.
- **Its own host:** it reaches the engine's machine as any Docker VM without network policy does: on Linux, its servers on every address but its loopback, through the gateway, and with IPv6 turned on, those listening on IPv6 too, through the bridge's link-local address; and other containers' ports published on the host's addresses, as any container does.
- **Root's files in the project folder:** on its ID-mapped mounts root writes as the host's root, as root in any Docker VM does: a file it makes set-user-id there is the host's root's, set-user-id, on the host, and runs as root for anyone who runs it. devvm names set-id files in the folder at each launch and stop on Linux hosts, root's apart (`setid_root_files`, checked); don't run programs from the project folder outside the VM.
- **Escapes through Sysbox**: a flaw in it, or in the kernel's user namespaces, reaches the host.
- **`docker exec -u` and groups added in place:** seen under Sysbox, a command `docker exec` runs as the VM's user doesn't get the `docker` group the layer adds in place, even after a restart (the VM's shell over ssh, a login, does). A VM without ssh, whose shell is a `docker exec`, can't use Docker without `sudo` then.

**Threat check** (the security-audit skill, its data isolation and local IPC companions). Leads, each confirmed and fixed, or ruled out:

- **A failed in-place add leaving a Sysbox VM** (`docker_layer=sysbox` with its image set back, so a VM with no layer that can't have network policy, under Sysbox for good): confirmed, fixed: a failed or interrupted script makes the VM as it was (`SetDockerLayer` off); unit-tested, and checked end to end with a layer whose script fails.
- **A reused network that isn't devvm's plain bridge** (one of devvm's by the VM's network's name, made again by someone with Docker access with IPv6, another gateway mode or other options): confirmed, fixed: only a plain bridge is reused, anything else is made again (the stopped container rejoins it by name; checked on Docker 29.1); unit-tested.
- **A container joining the VM's network between the check and its deletion** (`checkAlone`, then `removeNetwork`): ruled out as a way in. Only someone with Docker access can put one there; `removeNetwork` checks again, and Docker refuses to delete a network with a running container on it, so it fails rather than detach anyone's container.
- **The network and volumes made before the remake** (`Start`): ruled out. They must exist before the container that names them is made (Docker would make volumes unlabelled, and a missing network fails); a remake that fails leaves them labelled, for the next start or `rm`.
- **`NET_RAW` and `NET_ADMIN` under Sysbox** (frames forged on the bridge, routes to the host's loopback): confirmed that root has them, in its own namespaces, and `--cap-drop` doesn't take them away (Sysbox ignores it); what they reach is ruled out past its own bridge: checked, no stand-in on Docker's default network or another reached, even as root, and this machine's loopback not reached with `127.0.0.1` routed to the gateway, while a datagram to its server on every address arrives (the control).
- **The host's loopback with Docker's userland proxy off** (`"userland-proxy": false` in `daemon.json`): confirmed, not fixed: Docker 29.1 then turns `route_localnet` on for each bridge, adds no rule against it, and the datagram routed to `127.0.0.1` reaches this machine's server on its loopback (checked by hand on the docker host VM). Fixed: the VM's bridge's setting is read at creation and each start, and on (or unreadable) is refused (`docker_route_localnet`); unit- and CLI-tested.
- **IPv6 to the host:** confirmed (root turns it on and reaches the host's servers on `::`); the same servers are reached over IPv4 through the gateway, so it's the policy-less VM's reach, listed above, and the reason network policy is refused.
- **Network policy through some other path** (a launch, `Start`, `devvm network on`, adding the layer in place, a hand-edited state or record): ruled out. Each refuses it (`net_docker_layer`), the backend's `Start` by its own record, so neither devvm's state nor the backend's record alone can start such a VM through the proxy; unit-, CLI- and end-to-end-tested.
- **`services.sh`'s pid file** (deleting `/run/docker.pid` and `/run/docker`, shared with smolvm): ruled out. They go only when no `dockerd` runs by that pid (`/proc/<pid>/comm`), as root in the VM's own `/run`, which only root in the VM writes; a pid the VM reuses for another process no longer keeps `dockerd` from starting; checked: Docker's engine starts again after a restart, with its images.
- **Root's files on the project folder** (set-user-id files of the host's root's): confirmed, not fixed: the same as any Docker VM's root, listed above; what devvm says of them is fixed: set-id files of root's, or root's group's, are named apart, as running as root (`setid_root_files`), the rest as running as their owner (`setid_files`); unit-tested, and checked end to end.
- **The Sysbox package e2e installs:** ruled out. Pinned (0.7.1, the newest), both architectures' SHA-256 checked against GitHub's release digests; the AppArmor change only adds Sysbox's FUSE mounts under `/var/lib/sysboxfs` to fusermount3's profile, through its `local/` include.

**End-to-end checks** (`tests/e2e.sh --backend docker`; Sysbox on the Linux engine, which e2e installs, pinned, in its docker host VM):

- on Docker Desktop: refused in one line, new or added in place, nothing changed (`docker_layer_needs_vm`);
- on the Linux engine: with network policy, refused in one line, nothing made;
- runtime `sysbox-runc`, not privileged, said, unwarned, its engine's volumes, its own network, not internal, with the VM alone on it, `docker_layer=sysbox`, `net=off`; root's uid map isn't the identity, its bounding set has `NET_ADMIN` and `NET_RAW`; Docker's engine runs after each start and runs a container as the VM's user, which reaches the internet;
- a stand-in container of the sandbox's on Docker's default network, then on another network, isn't reached from the VM, even as root, while another container on that network reaches it (the control), and the VM reaches the internet;
- root in the VM, through its own Docker (a privileged container on the VM's network namespace), sends a datagram to this machine's server on every address through the gateway (it arrives: the control), then routes `127.0.0.1` to the gateway and sends to this machine's server on its loopback, which gets nothing; it turns IPv6 on and reaches this machine's server on `::` through the bridge's link-local address (Not covered);
- what the VM's user writes in the project folder is the user's; a set-user-id file root makes there is root's on the host, and the next launch names it as root's (`setid_root_files`);
- `devvm ls` shows it; `devvm network on` refused; restarted, its images kept; `rm` deletes its container, volumes and network;
- added in place to a base VM with a layer whose script fails: made as it was (Docker's runtime, without `NET_RAW`, on Docker's default network, its network and engine's volumes gone, `image=base`, no `docker_layer`), and network policy can be turned on; then added in place (through a terminal, confirmed): made again under Sysbox on its own network, its disk and home kept, Docker running in it.

## smolvm

Tried with smolvm 1.32.2 on an arm64 Mac before devvm had the backend ([its column](backends.md#features), [its page](../backends/smolvm.md)). The backend has its native features, network policy, emulated ([above](#network-policy-on-smolvm)), ssh for editors, emulated ([above](#ssh-for-editors-on-smolvm)), ports forwarded, every one or the listed ones, emulated ([above](#ports-on-smolvm)), and agent toggling, emulated ([above](#ssh-agent-toggling-on-smolvm)), all reviewed.

**Network policy.** smolvm's allow lists work per address, not per port, and DNS has its own path:

- With `--allow-cidr` of the host's gateway (`100.96.0.1`), the VM reaches every port on the host's loopback (ssh, local databases), not just the proxy's, and nothing else.
- Under any allow list, the gateway answers DNS for any name, even queries sent to `8.8.8.8`: a way out for data. `--allow-host-pattern` of a name that doesn't exist makes it answer NXDOMAIN, and then smolvm's process sends no query anywhere (checked with nettop: on its own network it queries the host's resolver itself). `--dns 127.0.0.1` makes it time out, but only `machine create` sets it.
- `--mediated-egress` with `--egress-interceptor` hands each connection the allow list admits to a host process, with its address, port and first bytes: it allows, denies, or takes the connection over. A test decider that took over only the proxy's port reached the proxy, and nothing else got through. It fails closed: with the decider gone, or a wrong token, connections are reset, and once started so, the VM won't start without one.
- A connection the decider will refuse still opens in the VM (smolvm collects its first bytes first), then resets: only data, not a connect, shows it's refused.

**How the backend fits the interface:**

- **Tool images:** uncompressed EROFS, since smolvm's kernel can't mount compressed ones. The tools build machine runs `assets/shared-tools/build.sh` as on Lima, then makes each image again without compression (`plain.sh`), so `build.sh` and Lima's tool keys stay as they are. A backend names its format (`ToolFormat`, `plain-<plain.sh's hash>`), which a tool image's key hashes when it isn't build.sh's own; one share holds both kinds.
- **No init system:** the image runs as a container in a microVM. While a build's scripts run, `systemctl` and `rc-update` are stand-ins that do nothing; after each start devvm makes the loop devices, mounts the tools and starts Docker where the docker layer installed it (`services.sh`). Docker's storage is `-v /var/lib/docker`, on the machine's own disk, on every VM, so the layer can be added in place. A project VM's setup tells a running systemd by `/run/systemd/system`, not by `systemctl` being there (Docker's packages install it).
- **Ubuntu's container image, not its cloud image:** before the scripts, base gets `ca-certificates`, `sudo`, `bash` and the VM's user (`prepare.sh`). The user has the host's name and uid, as on Lima: virtiofs shows the project folder as the host's uid, so `ubuntu` (uid 1000) couldn't write it; a user with that uid is removed first. `Built.Origin` is the image by its digest. The backend's own scripts that go into base are in its key (`KeyFiles`).
- **Network at create:** packs carry the build machine's network, CPUs and memory, and `--block-private` can't be removed from them, so builds use smolvm's default network and `CreateVM` sets everything. The network changes on a stopped VM (`machine update`), so `Start` sets it where it differs. For network policy, the decider's address and token come with `Confinement` (a backend with a decider implements `backend.Decider`), and the proxy is at the gateway.
- **ssh-agent forwarding is chosen at create:** `machine update` can't change it, so turning it on or off later is a feature of its own (`agent-toggle`), emulated by the agent each start names ([above](#ssh-agent-toggling-on-smolvm)). The agent socket is read at each start.
- **Every port** isn't something smolvm forwards, and listed ports aren't forwarded by smolvm either. Its forwards are at most 64, one of them ssh's, reach only servers on all addresses, and are set only while a machine is stopped. So `ports` and `ports-all` are emulated by a forwarder of devvm's ([above](#ports-on-smolvm)), and the VM's ssh is smolvm's only forward.
- **smolvm's forwards share a port.** A forward of smolvm's takes `127.0.0.1:PORT` and `[::1]:PORT` while a program on the host has `*:PORT`, and that program's connections to them go with it (checked on macOS), as they do for any Go listener, because both set `SO_REUSEADDR`. That's one more reason a VM's ports aren't smolvm's forwards. Each start, and each change of a running VM's ports, on every backend, first checks the listed ports with `platform.PortInUse`, which listens on each without that option, and leaves out the ports in use with a warning (`Confinement.Free`). devvm's forwarder binds without `SO_REUSEADDR`, and devvm checks the ssh ports it chooses, smolvm's and Lima's confined ones, the same way.
- **Lifeline:** smolvm's `agent.pid` has a second line, the start time, so the proxy reads only the first.
- **Ports** are set on a stopped VM, so `Confinement.SSHPort` is a forward set before the start, and `Confinement.SSH` says whether to run ssh at all: an emulation runs only once it's let through.
- **State:** `--state-dir` is Linux only, so on macOS devvm's machines share the user's smolvm, told apart by a label naming devvm's data folder; devvm acts only on machines with it. smolvm keeps a local usage journal; devvm turns it off (`SMOLVM_USAGE=0`).

## Docker

Tried with Docker 29.8 in Docker Desktop on an arm64 Mac and Docker 29.9 on Ubuntu 26.04 (arm64, rootful) before devvm had the backend ([its column](backends.md#features), [its page](../backends/docker.md)). Plain containers, unprivileged: every VM shares a kernel with the others, and on Linux with the host.

**What was tried:**

- **Building:** a container from `ubuntu:26.04` ran smolvm's `prepare.sh` and `shims.sh`, base's scripts as the user, the features and `sshd.sh`, then `docker commit`: 12 minutes (most of it the package snapshot's downloads), 1.1 GB, the commit 8 s. `--from alpine:3` built in 18 s once OpenRC and ssh's client were added first: base.sh writes an OpenRC service and `/etc/ssh/ssh_known_hosts`, and Alpine's container image has neither.
- **No init system:** systemd as PID 1 fails on the read-only cgroup tree Docker gives unprivileged containers, even with `CAP_SYS_ADMIN`; it runs only with `/sys/fs/cgroup` bind-mounted read-write, which hands root in the VM the whole host's cgroup tree, or `--privileged`. So, as on smolvm, `--init` (Docker's tini) runs a sleep, and devvm starts the services after each start (`services.sh` worked unchanged; a restart starts nothing). Stopping takes under a second.
- **Docker inside:** `dockerd` stops at its first iptables rule without `NET_ADMIN`, and runs with `--privileged`, which ends the VM's isolation (devvm never uses it), or under Sysbox, on Linux only ([the docker layer](#the-docker-layer-on-docker)).
- **Mounts:** the project folder and agents' folders bind-mounted; read-only ones refuse root, which can't unmount them. Docker Desktop shows the project's files as the VM user's, and the files it makes as the host user's, mode per umask; on Linux, files root makes are root's.
- **Shared tools:** containers get no loop devices, so not the EROFS images. Both of these worked read-only: a Docker volume of unpacked tools (tools a helper container adds show up in running VMs; `volume-subpath` mounts one folder), and each tool as an image mounted with `--mount type=image,image-subpath=…` (Docker 28 and later), its layers shared. A volume keeps the share's model: one copy, added to in place.
- **Limits:** `--cpus` and `--memory` apply, and `docker update` changes both on a running container. `--cpus` is a quota: coreutils' `nproc` counts it, BusyBox's doesn't, and `free` shows the whole machine. `--storage-opt size` is refused on Docker Desktop (it needs overlay2 on XFS with project quotas) and ignored by the containerd image store, Docker 29's default on Linux.
- **What a container reaches:** on Docker Desktop, the default network reaches the host's loopback (`host.docker.internal`, `192.168.65.254`). On Linux, it reaches the host's servers on all addresses through the gateway, not its loopback. An internal network (`--internal`) has no route out and resolves no outside names (no query left the host); on Linux it still reaches the host's servers on all addresses through its gateway, unless the network has no address of the host's (`-o com.docker.network.bridge.inhibit_ipv4=true`). Containers on one network reach each other, so each VM needs its own.
- **Ports:** `-p` is fixed when a container is made, reaches only servers listening on all addresses, and publishes nothing on an internal network. A forwarder container on the default network and the VM's, publishing the port, reached the VM's sshd on both engines; through it the VM reached only that port, back to itself.
- **Sockets:** a host socket bind-mounted on its own works on both. Docker Desktop shows it as root's, mode 0660 (root in the VM can `chmod` it there, not on the host), and connects by path at each connection, so a socket made again at the path is reached; while none is there, a connection hangs (10 s, then the client gave up). A socket in a bind-mounted folder can't be used on Docker Desktop (`Not supported`). On Linux the bind is the socket itself (a new socket at the path isn't seen), keeps its owner, and `chmod` in the VM changes it on the host; one in a mounted folder works, made after the start too. Docker Desktop's `/run/host-services/ssh-auth.sock` is the agent of the user's login, not one devvm chooses.
- **ssh:** `services.sh`'s sshd, published on the host's loopback, took the VM's own key alone; `ssh -L` reached a server on the VM's loopback, and `ssh -A` a throwaway agent.

**How the backend fits the interface:**

- **Made again where Docker fixes something:** a container's writable layer is the VM's disk, and Docker sets its mounts and network when it makes it. So the container carries a hash of what it was made with (`devvm.config`), and a start that finds the VM wants other mounts (agents' folders added or removed) commits it, makes a new container from the commit under a name of its own, deletes the old one and renames the new one: the disk is in the old container, then the commit, then the new one, and the record names the commit before the old container goes, so no stop on the way loses it. Each make adds a layer, so one past 100 is flattened (export and import); overlayfs stacks about 125. The VM's home is a volume of its own, so it stays out of the commits.
- **The host user's ids:** base's user has the host's name and uid, and on Linux its gid too (Dev Containers' `updateRemoteUserUID`, done when base is built, as images are per host), so files a VM makes in a bind-mounted folder are the user's; Docker Desktop maps ownership itself. A group with that gid that was the removed user's (Ubuntu's `ubuntu`) is renamed.
- **Shared tools in a volume:** each tool image is unpacked into one volume (`unpack.sh`, in a container of devvm's with no network, after the tools build, never in it), and `tools.sh` links a version folder that's a folder in the share where it would mount an image; mise takes linked version folders as installed. The format is a backend's own (`ToolFormat`: `dir-` and `unpack.sh`'s hash), so Docker's tool images are built for it, and stay in the share as the record of what's built: a start unpacks them again into a volume that's gone, and drops from it what `devvm gc` deleted from the share.
- **Build confinement:** native on an engine of this Linux machine, rootful (devvm tells by the engine's name being the host's), whose default network doesn't reach its loopback. Docker Desktop's reaches the Mac's, so builds there get network policy's parts instead, emulated ([above](#build-confinement-on-docker-desktop)); none on an engine devvm can't tell (another machine's, rootless, colima, OrbStack). An image built already needs no building: devvm asks for a build's features only when it builds.
- **Network policy:** an internal network per VM and a relay to the host's proxy ([above](#network-policy-on-docker)), rather than a proxy in a container: the proxy reads tokens from the Keychain and refreshes agents' logins in the user's files on the host, so a proxy in a container would need a way back to the host for both, and devvm's CA key and the tokens would be in Docker's VM on Desktop, shared with every container. The relay needs devvm's Linux build: on Linux devvm itself; on macOS one beside devvm or in `../libexec` (the Homebrew formula's, a source build's), or else a release's own, fetched (`linux.go`). A release's macOS binaries carry their Linux archive's address and the SHA-256 of the devvm in it (`registry.linuxURL`, `registry.linuxSHA256`, set with `-X`): `scripts/release.sh` builds the Linux binaries first on their own (`goreleaser build --id devvm`), takes their SHA-256s, then runs the release with them in the macOS builds' flags, and refuses a release whose Linux builds came out different the second time, or whose Linux archives' devvm isn't the pinned one. devvm fetches the archive the first time a Docker VM needs it, reads the devvm in it as it comes (gzip and tar, at most 256 MiB), and renames it into place only once its SHA-256 matches; then Go's build info must say it's the same build. Builds without a pin fetch nothing. Whatever was found is copied into devvm's data folder, which Desktop shares.
- **Disk:** none to set. The backend says what a VM holds instead (`backend.DiskUser`: its container's writes and its volumes), which `devvm size` shows and launches warn about past base's disk.
- **One transport for ssh, ports and the agent:** `docker exec` into the container, to an sshd in inetd mode per connection, behind ssh's `ProxyCommand` ([ssh](#ssh-for-editors-on-docker)): nothing published, nothing listening, the same on Docker Desktop and Linux and on any network a container is on. Ports go through smolvm's forwarder over it ([ports](#ports-on-docker)), and agents through ssh sessions alone ([agent](#ssh-agent-forwarding-on-docker)): a forwarder container publishing ports was tried and worked, but each VM would need one, and publishing fixes its ports when it's made; a socket mounted for the agent is fixed at create too, and reached by path differently on each engine.
- **The docker layer** needs a VM made for it ([above](#the-docker-layer-on-docker)): `docker-layer` emulated under Sysbox where the engine has it, none elsewhere, so a VM with the layer is refused there before anything's built or changed. A backend that makes VMs for the layer says so (`backend.DockerLayerVM`: the runtime it uses or its refusal, and making an existing VM one), and devvm records the runtime in its state (`docker_layer`) and refuses it network policy.
- **State:** Docker's engine is the user's, so devvm acts only on what carries its label, as on smolvm, and names what Docker names for everyone (images, the tools volume) with a hash of its data folder, so a test sandbox's never meets yours. Docker Desktop's file sharing list decides which folders a VM can mount: devvm reads it from Desktop's settings and refuses others before Docker would fail the start.

## devcontainer.json

A new VM gets what the project's `devcontainer.json` says, as far as devvm does it ([its page](../using/devcontainer.md)), on every backend.

**The guarantee:** nothing from the file runs on or reaches this machine: it reads none of its environment, files, credentials, Docker images or registry logins, adds no mount, writes nothing to the project folder, and weakens no confinement (network policy, `.git` protection, the Docker backend's rules, the docker layer's Sysbox-only rule). It shapes only what's in a new VM and what runs in it, as the VM's user. devvm's own handling of it (reading, parsing, state, the environment file, commands, ports, the image lookup) can't be turned against this machine or devvm. Reviewed: the threat check's leads are fixed, ruled out or listed below.

**The problem:** the file is the project's, so the VM's: the VM writes the folder, and a cloned repo's file is whoever wrote it. Dev Containers runs much of it on the host (`initializeCommand`, `${localEnv:…}`, builds, `mounts`, `runArgs`, docker-outside-of-docker's socket), pulls images with the user's logins, and forwards ports at will.

**How it's kept:**

- **Reading:** only in the folder, through `os.Root` (a link out of it isn't followed, `..` included), opened without blocking (a FIFO the VM made in its place opens at once and is refused) and checked as a regular file on the open descriptor, at most 1 MiB. It's read once, at `plan`; what the VM is made from is the parsed plan, recorded in its state, never the file read again. Later launches only hash it and warn.
- **Parsing:** comments and trailing commas are blanked at the same offsets, strings untouched, then `encoding/json`; values of the wrong kind, a NUL, an environment variable's name that isn't one, and every variable devvm doesn't fill in are refused before anything's made, `${localEnv:…}`/`${env:…}` above all. Nothing is filled in from this machine: `${containerWorkspaceFolder}` is the folder's path (the same in the VM), `${containerEnv:X}` the VM's own `X`, left to its shell.
- **Mapped, or refused, or ignored:** `build`/Dockerfiles/Compose are refused; `initializeCommand` never runs; `mounts`, `runArgs`, `privileged`, `capAdd`, `securityOpt`, `workspaceMount` and the rest are ignored, named. Features map only to devvm's own layers (docker-in-docker to the docker layer, four toolchains); no feature's script is fetched, `docker-outside-of-docker` is refused, everything else too.
- **The image:** `--from`'s path, but only an image its registry gives anyone: asked anonymously (`from.Lookup.Public`, never Docker's store), pinned to that digest, which every backend pulls by. A registry named `localhost` or by an address that isn't the internet's is refused by name, and the lookup's client (`from.NewPublicRegistry`) connects only to the internet's addresses, whatever a name resolves to, its token service's included; offline, only a registry digest recorded for that reference stands in.
- **The docker layer:** the backend's own rules for it, as when it's named; on Docker, where a VM with the layer can't have network policy, the VM is made without it, unasked and warned (`chooseNet`, `net_off_docker_layer`), as when the layer is named, and `--network-policy` refuses it: the file takes network policy away only where devvm says so.
- **The environment:** each variable's value is built as a shell word (single-quoted text, `"${X}"` for the VM's own), stored as JSON in the VM's state, and written as `export NAME=word` into the VM's environment file before devvm's own (which win); a name is checked again when it's written.
- **Commands:** stored as argv in the VM's state; run by the backend's `Exec` (Lima: one `sh -c` string, each word `shq`-quoted; smolvm and Docker: arguments as they are), as the VM's user, in the folder, after the self-check, `.git`'s locks and a `--clone` VM's clone: confined like anything in the VM. Their output goes to the run log, shown only through `printable`.
- **Ports:** only numbers and `localhost:N`/`127.0.0.1:N`, and never beyond the user's ports (`devvm ports -g`, or `--ports`, which wins): with every port forwarded, the default, they're among them; ports the user's list leaves out are said (`devvm ports add` forwards them), not added (`devcontainer_ports_not_forwarded`). Forwarded on this machine's loopback as any listed port, never a host port of another program's (`ports_taken`).

**What it relies on:** `os.Root` and `O_NONBLOCK`; `encoding/json`; each backend's `Exec` passing arguments unchanged; the registry's digest naming what's pulled (a pull checks it); the backend's own confinement of the VM and its builds.

**What could break it:** a backend whose `Exec` runs its arguments through a host shell; a new property mapped without the same review; a host proxy that reaches this machine or its network for a public-looking name (Not covered).

**Not covered:**

- **The project's own VM.** The file decides what's in it and runs commands in it from its first start: the VM is the project's ([security](security.md#what-it-doesnt-protect)). Its `image` is any public image, whose code runs as root in the build VM, as with `--from`.
- **Through a host proxy** (`HTTPS_PROXY`), the lookup reaches what the proxy does: only names are checked, not what the proxy resolves them to.
- **A name that resolves to the internet for devvm and to this machine's network for the backend's pull** (DNS rebinding) gets only content with the digest the public registry gave, which only someone who has that content can give.

**Threat check** (the security-audit skill; its local IPC, data isolation and supply chain companions). Leads, each confirmed and fixed, or ruled out:

- **An image only this machine or its network has** (`localhost:5000/…`, a private address, a name that resolves to one, its token service on one): confirmed: Docker's backend pulls it with the engine (on Linux, this machine's loopback), and the lookup was made on this machine; fixed: refused by name and by address (`publicHost`, `NewPublicRegistry`), a recorded digest included; unit-, CLI- and end-to-end-tested.
- **docker-in-docker taking network policy away on Docker** (the question skipped for a VM made for the layer): confirmed, fixed: asked, a yes refuses it; unit-tested.
- **forwardPorts over a user's port list** (added to `devvm ports -g`'s list, or to `none`, a limit the user set): confirmed, fixed: the user's ports win, the file's beyond them are said, not added; CLI- and end-to-end-tested.
- **The JSONC stripper and parser** (comments in strings, an unterminated comment or string, a BOM, trailing commas): ruled out: blanking keeps offsets and leaves strings alone; anything else is invalid JSON; fuzzed (`FuzzParse`): no panic, every variable a shell word, nothing of this machine's environment kept.
- **Reading** (a link out, `..`, a FIFO, a device, a huge file, a swap between the check and the read): ruled out: `os.Root`, a non-blocking open, the descriptor's own `Stat`, 1 MiB; one read per new VM; unit-tested (links, a FIFO).
- **Variables** (`${localEnv:…}`, `${env:…}`, nested or unterminated): ruled out: refused, or left as text for the VM's shell; nothing is read from this machine.
- **The environment file and state** (newlines, quotes, `$()`, a name like `A;rm`): ruled out: values are shell words, JSON-escaped in state (one line), names checked twice; the file is the VM's own.
- **Command quoting** (`'`, newlines, an argument starting with `-`): ruled out: every backend runs `bash -lc 'exec "$@"'` with the argv after it; Lima quotes each word; smolvm passes `--`.
- **Messages** (the file's values in this machine's terminal): ruled out: VM-made values go through `msg.Shown`, the image through `from.Valid`, errors' causes aren't printed, the log tail is `printable`.
- **Commands before confinement:** ruled out: they run after the self-check (which stops a VM whose policy fails), `.git`'s locks, and a clone's seeding.
- **A digest the registry made up** (`Docker-Content-Digest`): ruled out: `sha256:` and 64 hex digits, and every pull checks content against it.

**End-to-end checks** (`tests/e2e.sh`, `project`): a VM made from a file: its variables in the shell, `postCreateCommand` once and `postStartCommand` at each start, in the VM and folder, its port forwarded and no other, nothing written to the folder, a changed file only warned about; a file whose image is on this machine's registry refused, nothing made.

## A company proxy

Behind a company proxy, nothing reaches the internet without going through it, so network policy's proxy goes through it too ([how](network.md#through-a-company-proxy)), and each build goes through a proxy of devvm's for the build alone, which goes through it. The design keeps two things: the proxy still decides every request by the name the VM asked for, and the company proxy's password reaches nothing of a VM's or a build's.

**What it's built from:** the host's `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`, read from devvm's environment (`backend.ReadHostProxy`) when a VM's proxy starts, checked (`HostProxy.Upstream`: only `http://` proxies), and written to `run/<vm>.proxy.upstream` (mode 600) for `devvm _proxy -upstream` (`internal/proxy/upstream.go`). The proxy opens its own `CONNECT` through the company proxy, by name, with `Proxy-Authorization: Basic` from the URL, for tunnels and for the TLS connections it makes to put secrets in, which check the server against the system's roots and the user's CAs. Plain HTTP goes to the company proxy in absolute form. A change to the settings starts the VM's proxy again at devvm's next run, and an old proxy that won't stop fails the start (`proxy_stop_failed`) rather than run on with its old settings.

**What an upstream changes:** the proxy resolves a name and dials the addresses it checked only when it connects directly. Through a company proxy, the company proxy resolves the name, so the floor can't hold it to checked addresses:

- An address the VM asks for is judged as before, and `localhost`, `*.localhost` and loopback and unspecified addresses never go upstream, so the floor refuses them as before unless a rule names them. A host whose last label is all digits or starts with `0x` (`127.1`, `2130706433`, `0x7f000001`) is refused as no host name (`hostOK`), because a company proxy that reads it as `inet_aton` does would reach an address the floor never judged.
- A name is refused when this machine's resolver answers with any internal or denied address (`floorUpstream`). A name this machine can't resolve within three seconds goes upstream unjudged only when the policy names it, as itself or under `*.domain` (`policy.byName`). When only `**` allows it, the proxy refuses it (`errUnresolved`), because `**` would otherwise send the company proxy any name the VM makes up, and the company proxy may resolve such a name to its own network's hosts.
- The company proxy may still resolve a name differently, or later, than this machine did (DNS rebinding between the two lookups). A VM that controls a name under an allowed domain can choose the unjudged path: its name server can fail, or answer after the proxy's three seconds, and then answer the company proxy with an internal address.
- So under a name the policy lists, a VM reaches whatever the company proxy reaches: its company's internal hosts, and the company proxy's own host, including this machine's loopback when the company proxy runs on this machine (a local proxy that a VPN client runs, for example). Address denies apply only to the addresses this machine resolves. The allowlist stays the limit: a name the VM's policy doesn't allow never reaches the company proxy.
- The proxy reads at most 64 KiB of the company proxy's answer to `CONNECT` (`maxConnectReply`), so an answer whose headers never end fails the request instead of filling memory.
- The company proxy sees every allowed host name and port, and with a CA in the user's CA folder, it reads TLS too, as it does for this machine.

**Credentials:** the company proxy's user and password are in no process's arguments (only the file's path is), in no log (the event log's `upstream` field and the proxy's own log name the company proxy as `host:port`, and the URL the proxy's HTTP transport uses has no user), and in no request but the company proxy's own: the proxy drops the VM's `Proxy-Authorization` and sets the company proxy's only for a request it sends there. The VM never sees them, not even in a refusal, which names the company proxy by `host:port` and its status code.

**Builds:** a build runs code that isn't devvm's: layer scripts run third-party installers, and with `--from`, the container image's own shell and package manager run as root in the build VM. So a build never gets the company proxy's settings. Behind a company proxy, each build goes through a proxy of devvm's on the host for that build alone (`backend.ProxyStarter`), the one Docker Desktop's builds use ([build confinement on Docker Desktop](#build-confinement-on-docker-desktop)). It's `devvm _proxy` with a policy file of `**`, which allows any host on ports 80 and 443 but the host's own and internal addresses, a new random password in a file, the company proxy's settings in its `-upstream` file, and `-lifeline` on the build VM's hostagent or the build container's `docker container wait`. The build gets only `http://devvm:<password>@<host>:<port>`, in each proxy variable the host sets, and the host's `NO_PROXY`. When the build ends, devvm stops that proxy and deletes its password and upstream files, and a successful build's folder goes too. The password is worthless once the proxy has stopped, and the build never sees the company proxy's address, user or password. Without a company proxy, builds start no proxy and get no proxy settings.

- **Lima:** the build VM (an image's, the tools build's or `--from`'s conversion VM) reaches the proxy at `192.168.5.2`, the host's address on Lima's user-mode network, with vz and with QEMU, and on macOS its Seatbelt profile allows that one port of the host's loopback alongside its ssh port. The proxy runs on the host, so a company proxy on this machine's loopback, such as one a VPN client runs, works for builds on macOS too. Lima's `propagateProxyEnv` would write the host's proxy settings into the guest's `/etc/environment` between `#LIMA-START` and `#LIMA-END` at each boot (Lima's `07-etc-environment.sh`), and a stopped build VM's disk would keep that block, so build VMs start with `propagateProxyEnv: false`, and only VMs on Lima's own network (`NetDirect`) start with it on. Lima also logs the proxy settings it reads, password and all, into devvm's run log, so devvm runs `limactl` without them, and only a `NetDirect` VM's start gets them back. Each build script gets the build proxy's variables exported at its start, on its input with the script (`internal/backend/lima/buildproxy.go`), and `/etc/sudoers.d/devvm-build-proxy` keeps them for `sudo` until the scripts end.
- **`--from`'s conversion:** `oci/build.sh` runs as root with the build proxy's variables for crane. The container image's own code runs only in a chroot under `env -i`: the `/etc/os-release` check gets `PATH` alone, and `chroot_run` (`bootify.sh`, the CAs' `ca.sh`) gets `PATH`, `HOME`, `LC_ALL` and the build proxy's variables, for `bootify.sh`'s package downloads.
- **Docker:** a build behind a company proxy gets what a build on Docker Desktop gets on any engine (`buildNet`): an internal network of its own, its relay and the build's proxy, whose address its commands read from an env file. So on a Linux engine, a build behind a company proxy needs devvm's Linux build, as network policy does. Docker's client puts the proxies in `~/.docker/config.json` into each container it makes, and a commit keeps them, so devvm makes every container, VMs, builds, relays and the tools' unpacking, with each proxy variable set empty (`noClientProxy`).
- **smolvm** passes the host's proxy settings into a machine only with `--use-host-proxy`, which devvm doesn't use, so its builds get no proxy settings.

The build's policy is `**` alone, so on its own the build's proxy would refuse every name this machine can't resolve, and where only the company proxy resolves outside names, a build would reach nothing by name. Lima's and a Linux engine's build proxies start with `-upstream-unresolved`, which sends such names on to the company proxy unjudged. The refusal would protect little there, because without a company proxy those builds are on Lima's user-mode network or Docker's own and reach internal addresses directly. Docker Desktop's build proxy starts without it: Desktop's builds go through devvm's proxy to keep them off this machine's own services, and a company proxy on this machine's loopback could resolve a name the build makes up to `127.0.0.1`.

**End-to-end checks** (Lima):

- `images`: a layer built with a fake company proxy's password in `HTTPS_PROXY` and `HTTP_PROXY` (a closed port, `NO_PROXY=*`): its script and `sudo` see the build's proxy at `192.168.5.2` with user `devvm`, never the password, the build's proxy is gone afterwards, and neither the image's whole disk, nor Lima's files for it, nor devvm's logs hold the password;
- `from`: a company proxy of the run's own with a password, and a `--from alpine:3.21` base, with every feature, and a layer on it: the registry, Alpine's mirror and the layer's own download reach the company proxy through the builds' proxies; what the layer's commands and `sudo` have is the build's proxy with a password of its own; and the password is in no converted disk, image, log, build file or process's arguments;
- `network`: a company proxy of the run's own (a `devvm _proxy` with a password, allowing any host): the VM's next launch with it in devvm's environment starts the VM's proxy again with `-upstream`; an allowed host goes through it by name (its event log) and the VM's event log names it; a host the VM's policy doesn't allow gets `403` and never reaches it; its password is in no process's arguments, no log and nothing of the VM's; the launch after, without it, starts the VM's proxy again going directly.

**Not covered:** `https://` and `socks5://` company proxies, which devvm refuses (`upstream_proxy_scheme`); proxy auto-configuration (PAC) files and the macOS system proxy, which devvm doesn't read; Kerberos or NTLM authentication. A Lima VM without network policy gets the host's settings in its `/etc/environment` by Lima's design, and turning network policy on for it later leaves them in the disk's free space.

## The desktop

`devvm desktop` shows a VM's desktop on this machine with VNC, on every backend, and keeps two things: no one on this machine or the network reaches the desktop without the VM's password, and the desktop gives the VM no new way out. Both hold whatever the VM's own server does, because root in the VM can replace it ([how](desktop.md)).

**What it's built from:** the `desktop` feature (`assets/features/desktop.sh`): Xfce and TigerVNC's `Xvnc` from base's package snapshot, and `/usr/local/bin/devvm-desktop`, which starts `Xvnc` on a socket of the VM's user's own (`/run/devvm-desktop/vnc.sock`, mode 600 in a 700 folder), with no TCP port and no password, then an Xfce session. On this machine, `internal/desktop`'s `Relay`, which `devvm desktop` runs (`internal/vm/desktop.go`): a listener on `127.0.0.1` alone (`platform.ListenLoopback`, without address reuse), on the port the VM's state records (`desktop_port`, among `netpolicy.UsedPorts`), and for each viewer that passes its check, an `ssh -W` channel to the socket through devvm's ssh config's entry for the VM. The feature isn't chosen until you choose it (`desktopFeature`), because it adds about 370 MB to base.

**Why devvm's own relay, not the port forwarder:** the forwarder forwards every port a VM listens on from its start, on the same port number. A VNC server on a port would have been on this machine's loopback at every start, without anyone running `devvm desktop`, on a port another VM's desktop or macOS's own Screen Sharing server (5900) can have. The relay is open only while `devvm desktop` runs, on a port of the VM's own, and checks the password itself, which the forwarder, a byte copier, can't.

**The password:** VNC's own authentication (RFB security type 2: DES of a 16-byte challenge, `desktop.Response`) is what macOS's Screen Sharing speaks to a server that isn't a Mac, and it takes 8 characters. devvm's are random, from 31 characters (about 40 bits), checked one at a time with a second's wait after a wrong one, so an online guess takes thousands of years. The relay checks it before it starts any ssh, so a wrong viewer costs the VM nothing. It's kept in the VM's state (`desktop_password`, mode 600), shown only with the address (`desktop_ready`, a message, not the run log), and never sent to the VM, so a VM, including a Docker Desktop VM that reaches this machine's loopback, can't use it to reach its own desktop's port. Screen Sharing gets the address alone (`open vnc://127.0.0.1:PORT`), not the password, which would be in `open`'s arguments where any process on this machine reads them.

**What keeps the VNC connection from carrying the VM out.** Every connection starts on this machine: a viewer connects to the relay, and the relay asks devvm's ssh for a local channel (`-W`) that the VM's sshd connects to the VM's own socket. The ssh asks for no session, agent, X11, tunnel or remote forward, and OpenSSH's client refuses a channel the server opens unasked, as for [the forwarder](#ports-on-smolvm). What the VM sends back goes only to the viewer that connected. The VM's server reaches nothing on this machine, so network policy holds as it is: the VM's own connections still reach only its proxy, and devvm allows no new host for the desktop.

**The clipboard:** off unless `--clipboard`. Without it, `Xvnc` starts with `AcceptCutText`, `SendCutText`, `SetPrimary` and `SendPrimary` off, and the relay drops every `ClientCutText` from the viewer, extended clipboard ones too (`internal/desktop/filter.go`). It reads the viewer's messages by their lengths (RFC 6143's and the extensions TigerVNC offers: fences, continuous updates, desktop size, xvp, GII, QEMU's key and audio events) and ends the connection on a type it doesn't know, so nothing it can't read reaches the VM. The other way, from the VM to the viewer, isn't read: following the server's `ServerCutText` would mean decoding every screen update's encoding. A VM whose server was changed can send its clipboard to the viewer, so Screen Sharing's Use Shared Clipboard setting is what keeps it off this machine then.

**End-to-end checks** (`tests/e2e.sh`):

- `desktop` (Lima, a base VM with network policy): the relay on `127.0.0.1` alone, its port and password in the VM's state; a wrong password refused, the password let in, with the VM's ServerInit and a screen update (`TestE2EDesktop`); `Xvnc` on its user's socket (700, 600) and no TCP port, the clipboard off; the password in no file of the VM's, no run log and no host process's arguments while `devvm desktop` started; the self-check passed and no direct connection out, nor to the desktop's port on this machine; root's own server in place of `Xvnc` (no password, its socket anyone's, recording what reaches it): a wrong viewer never reaches it, and the viewer's clipboard never does while its key event does; Ctrl+C closing the port; `--clipboard` on the same port, the clipboard on;
- `--backend smolvm` and `--backend docker`: the relay on `127.0.0.1` alone (on Docker, the container publishing nothing), a wrong password refused and the password let in, `Xvnc` on its user's socket and no TCP port, the clipboard off, the password in no file of the VM's or run log, Ctrl+C closing the port.

**Not covered:** the VM's clipboard sent to a viewer that takes it, by a server root changed; Screen Sharing itself, which no check drives, so its messages are the relay's reading of the protocol; a program on this machine with the password, which reaches the desktop as you do; a program on this machine, or a VM that reaches this machine's loopback, that keeps the relay's 8 connections busy or keeps failing its check, which keeps viewers out for as long as it does, and gets no further.

## Shared tools

Each tool version is one compressed EROFS image, loop-mounted read-only in each VM from a read-only share ([details](../using/images.md#shared-tools)).

- **Measured (macOS):** ten tools take 0.85 GB as images (1.5 GB installed), once for every VM and mix. Start times from an image match a local disk warm (`node -e 0` 13 ms vs 14 ms, `claude --version` 3 ms), and are 10–30 ms slower cold. Mounting five images takes 0.15 s; VM start is unchanged.
- **Why images, not a shared folder:** tools run from a virtiofs folder were about 3× slower warm (`node -e 0` 38 ms, `claude --version` 30 ms), the Mac's case-insensitive disk collided 33 file names in Python's terminfo, and mise's version links failed in a read-only folder.
- **Why not per-tool layers:** an image chain for every mix of languages and agents repeats each agent's files in every mix.
- **Why a tool that doesn't mount fails the launch:** mise would otherwise download the same version into the VM on first use, which gives that VM a private copy, a download nobody asked for, and one that network policy may block, all without a word ([how](images.md#the-share)).
- **Instead of Nix:** Nix and NixOS were weighed and rejected: NixOS breaks prebuilt binaries, and a hidden Nix shows through read-only-store errors.

## Linux hosts: overlays instead of copies

Lima on QEMU keeps one qcow2 disk per VM, and a clone copies it (2.0 GB for `base`). A project VM's disk is a qcow2 overlay of its image's instead ([details](lima.md#clones-and-overlays)): 196 KB new, 12 MB after booting, the same speed except fsync writes (1.8–2.5 s vs 1.2–2.1 s per GiB). Flattening one (`qemu-img rebase -b ""`) took 8 s, if it's ever needed.

## One binary

devvm's own files (`assets/` in the repo: `base.yaml`, `layers/`, `features/`, `shared-tools/`, `guest/`, `oci/`, `container/`, `smolvm/`, `docker/`) are embedded in the binary (`assets.FS`), so devvm installs, moves and upgrades as one file and can't find a mismatched copy beside it. Code reads them from that file system; scripts reach VMs on their standard input, never by path or file mode. Only what needs a path gets one: the whole set is written out to `~/.local/share/devvm/assets/<hash>` (16 hex digits of a SHA-256 over each file's name and contents), files 600 and folders 700, built in a temporary folder beside it and renamed into place, so concurrent runs share the first complete one. That's `base.yaml` for `limactl create`, `oci/` mounted read-only into `--from`'s build VM (root there reads it), with `guest/` beside it when you have [company CAs](network.md#a-companys-ca), and the policy files a VM's proxy reads, by path, for as long as it runs. `devvm gc` deletes older copies except those a proxy was started with.

## devvm's own Lima home

Lima merges `_config/default.yaml` and `override.yaml` of its home into every VM. In `~/.lima`, a `networks: [{vzNAT: true}]` there gave a VM with network policy a second network card with a default route around its proxy (the self-check caught it), and an extra mount went unnoticed. Hence a Lima home of devvm's own, which refuses those files and any network devvm didn't give a VM ([details](lima.md#a-lima-home-of-its-own)). The costs: plain `limactl list` doesn't show devvm's VMs, and VM names are shorter, as Lima's ssh socket path is at most 104 characters.

## Failed attempts

- **Claude's host login in VMs:** on macOS it's in the Keychain, which can't be shared. VMs use a `claude setup-token` token instead. The first token saved was the code the browser shows, so `devvm auth claude` refuses one without the `sk-ant-oat01-` prefix.
- **krunkit (Lima on libkrun) to return freed memory:** it didn't visibly return any.
- **Debian's arm64 cloud kernel for `--from`:** it has no `gpio_keys`, so it ignored Lima's stop request; Lima hard-killed the VM after 30 s, and node, bun and dockerd in the image came out corrupted. `--from` uses the generic kernel.
- **Every layer as a Docker build stage, flattened:** it worked, but each image became its own full disk (3.7 GB for `node`).
- **Shared read-only layers:** each Docker layer as an EROFS file, stacked as `/` with overlayfs over each VM's own disk by an initramfs of devvm's own. It worked (`node` took 1.0 GB of layers instead of a 1.8 GB disk), but devvm owned the boot path (the initramfs, an exit initramfs for clean shutdowns, kernel extraction), and cold program starts were 10–50 ms slower. Shared tools, and overlays on Linux, give the same savings without it.
- **A read-only mount for `.git/hooks`:** root in the VM can unmount it and write hooks through the project mount underneath. Locking `.git` itself (`uappnd`) breaks git, and a locked placeholder `.git/commondir` makes git fail. Hence `chflags uchg` on hooks and config, plus detection ([details](../safety/git-protection.md)).
- **Kernel extraction trying gzip first:** Ubuntu's arm64 kernel is an EFI executable with a zstd payload.
- **`mke2fs -d` from a tarball:** it needed libarchive and a UTF-8 locale. A directory works.

## Things learned

- **Lima `vz` never returns freed guest memory to the Mac.** sbx returns it with a VM monitor of its own; libkrun has `MADV_FREE`, with a stronger fix still an open PR; smolvm's libkrun fork includes it.
- **APFS clones** cost nothing until written, and `du` overcounts them: real use was 5.5 GB where `du` said 12.7 GB.
- **Lima locks each additional disk to one running VM,** so images shared across VMs go through a shared folder (virtiofs on macOS, 9p on Linux) and are loop-mounted from it.
- **Read-only mounts are enforced by the host:** even root in the VM can't write to them, but root can unmount a nested one and reach what's underneath.
- **Codex and opencode refreshing their OAuth logins in a VM can rotate the token and sign the host out.** With network policy the VM holds only placeholders and the proxy refreshes on the host (`internal/proxy/logins.go`). Codex decodes `id_token`'s claims and the access token's `exp` without checking signatures, so placeholders are unsigned JWTs with the real account claims and a far-off `exp`.
- **No existing tool** gives Lima Dockerfile-style layers with sharing at run time; smolvm, nerdbox and Kata do it on VM runtimes of their own.
- **Where devvm fits,** next to sbx, smolvm and Colima: sbx puts agents first; devvm gives a full Linux VM per project, with agents optional.

## Open work and risks

User-facing limits are in [Known limits](../using/limits.md) and [what the security model doesn't protect](security.md#what-it-doesnt-protect).

- **`--from`:** a moved tag is noticed only at the next build, not when listing images; devvm doesn't log in to registries, so private images work only through Docker; registries over plain HTTP (`localhost:5000`) aren't supported.
- **Alpine:** `rc-status` as a normal user shows `acpid` and `syslog` as crashed, as their pid files are root's (`sudo rc-status` is clean).
- **Free-space floors:** the free space devvm wants before each build and new VM ([free space](../using/ports-size.md#free-space)) is set by Lima's and smolvm's own packages, and for shared tool images in `internal/backend/disk.go`, where the comments give what each number was measured from. The measurements are free space, read with statfs before, during and after each step, in e2e runs on macOS with Lima `vz` and smolvm and on Docker's Linux engine. On Linux hosts, Lima's numbers add a copy of base's disk to an image's and a tools build's, but they haven't been measured there yet. A `--from` base converts its image in the host's temporary folder, which devvm doesn't check, because on Linux that's often a small tmpfs.
- **x86_64 hosts** are untested on real hardware; on Intel Macs, `--from`'s kernel is untested with `vz`.
- **Linux hosts:** the QEMU wrapper depends on the shape of Lima's `-netdev user,id=net0,…` argument. If Lima changes it, the wrapper refuses to start QEMU rather than run it unrestricted.
- **Network policy, not built:**
  - tokens for services devvm doesn't know: a host, a header, a format and an environment variable;
  - method and path rules on decrypted hosts, such as read-only GitHub, or no `git-receive-pack` unless approved;
  - approving blocked hosts as they're hit;
  - Claude's `/login` OAuth, refreshed in the proxy (`setup-token` works, so maybe never).
- **Network policy, risks of the mechanism:**
  - `sandbox-exec` is deprecated. If Apple removes it, macOS needs another way to confine the hostagent: an egress filter upstream (gvisor-tap-vsock#609 and #631; Lima's `hostLoopback: false`, lima#5581), a user-v2 daemon of devvm's own (lima#5464), or QEMU with the Linux mechanism on macOS too (it works there, slower than `vz`). The self-check catches it breaking silently.
  - VMs started outside devvm (`limactl start`, `limactl shell` starting a stopped VM, Lima's start at login) aren't confined: devvm reports them `unenforced`. An `override.yaml` setting a dead `HTTPS_PROXY` might harden this (untested).
  - A Lima upgrade that adds a hostagent connection fails closed: the start hangs until Lima gives up (10 minutes in the experiment). devvm should time-box the start and say it's the sandbox. That includes unix sockets: the profile allows only those in the VM's Lima folder and the forwarded agent's. Allowing every unix socket would let a compromised hostagent reach `docker.sock` or another ssh agent.
  - Tunnels the proxy doesn't read are decided by the `CONNECT` host and checked against the TLS server name, so domain fronting through a shared CDN may still reach other hosts.
