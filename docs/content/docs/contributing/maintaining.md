For maintainers: version bumps and releases. Run the scripts with mise, which puts the pinned GoReleaser and minisign on `PATH`: `mise exec -- scripts/release.sh`.

## Updating pinned versions

- `scripts/bump.sh --check` lists every pin against upstream; `scripts/bump.sh [tool...]` rewrites the pins (all tools by default) and prints a summary for the commit message. It writes a value only if it has the shape of a pin (a version, a 64-hex checksum, a dated release, a commit), since some of the edited files run on the host, and edits nothing unless every value is good. It needs `curl` and `jq`.
- The tools: `docker`, `nix`, `direnv`, `nix-direnv`, `mise`, `rustup`, `crane`, `omb`, `eza`, `tealdeer`, `e2e-tools`, `e2e-from`, `e2e-ubuntu`. base's Ubuntu cloud image and its apt packages have nothing to bump: devvm pins the newest image on each machine at its first build of base, and records the newest packages for each key of base at its first build ([Ubuntu's cloud image](../internals/images.md#ubuntus-cloud-image), [base's packages](../internals/images.md#bases-packages)). `docker` moves Docker's packages (`assets/layers/docker.sh`), read from its repository for base's Ubuntu release, and its signing key. Packages added to `assets/layers/base.sh` or `assets/features/` need no pin of their own: they change base's key, whose first build records them.
- `mise` moves base's mise (`assets/layers/base.sh`) and devvm's host mise (`internal/tools/mise.go`) together: the host one writes the lock base's installs from. `TestMisePins` fails when their versions or Linux checksums differ, and base's mise version is in the key of each tool image mise installs, so a bump builds them again.
- The shared tools aren't pinned for users: holds go in `assets/shared-tools/mise.toml` (`node = "24"` stays on that major). `testdata/mise.lock` is a fixed lock for the tests.
- `e2e-tools`, `e2e-from` and `e2e-ubuntu` move the end-to-end tests' own pins, which keep their cached images valid between runs: `e2e-tools` resolves `tests/e2e-mise.lock` again, with devvm's pinned host mise, for both architectures' glibc and musl VMs, and refuses a tool whose download has no checksum on every platform yet; `e2e-from` moves the digests of `node:24`, `alpine:3` and `ubuntu:26.04` in `tests/e2e/from_test.go` to Docker Hub's; `e2e-ubuntu` moves `e2e_ubuntu_release` in `tests/e2e.sh`, the dated release of Ubuntu's cloud image that e2e pins base to in place of the newest, to the newest Ubuntu lists. Ubuntu removes dated releases after a few months, and e2e's going stops its first builds of base: bump `e2e-ubuntu` before that. Run `e2e-tools` after any change to `assets/shared-tools/mise.toml`, because `tests/e2e.sh` refuses a lock resolved from another one ([end-to-end tests](_index.md#end-to-end-tests)). `mise run test` catches it first: `TestE2ELockPins` checks the lock's first line against `mise.toml` and that it locks each of its tools, and `TestE2EUbuntuPins` checks that `e2e_ubuntu_release` is a dated release of base's Ubuntu release, which `e2e-ubuntu` lists, and that both scripts name only that release.
- `assets/layers/ubuntu-cloud.gpg` is Ubuntu's cloud image signing key (fingerprint `D2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81`), from keyserver.ubuntu.com. If Ubuntu changes it, pinning a new image (a first build of base, or `devvm rebuild base`) stops with `ubuntu_bad_signature`: fetch the new key, check its fingerprint against Ubuntu's announcement, and replace the file (`gpg --export FPR`).
- `assets/layers/ubuntu-archive.gpg` is Ubuntu's archive signing key, "Ubuntu Archive Automatic Signing Key (2018)" (fingerprint `F6ECB3762474EDA9D21B7022871920D1991BC93C`), fetched from keyserver.ubuntu.com by that fingerprint, checked against the fingerprint that [Ubuntu's security team lists](https://wiki.ubuntu.com/SecurityTeam/FAQ), and exported with `gpg --export-options export-minimal --export FPR`. devvm checks the `InRelease` files of a first build of base against it (`ubuntu.ArchiveKeyring`). If Ubuntu signs the archive with a new key, that build stops with `packages_refused`: fetch the new key, check its fingerprint the same way, and replace the file. The key must be RSA, because `internal/ubuntu/pgp.go` checks only RSA signatures. Moving base to a new Ubuntu release (`ubuntu.Series`, `ubuntu.Version`) also moves `ubuntu.Released`, the day Ubuntu released it, which is the date of that release's own `InRelease` (`dists/<series>/InRelease`), because devvm refuses a release pocket dated before it.
- Edited scripts change image keys, so the affected images rebuild on next use. An edit to `assets/prelude.sh` changes the key of every image and every shared tool image. Build them in a sandbox of their own (`LIMA_HOME`, `DEVVM_LIMA_HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`) before committing (`devvm build docker`, or a VM made with the tools whose build script changed), then `devvm gc`, and run the [end-to-end tests](_index.md#end-to-end-tests).

## Checking base against Ubuntu's newest

The end-to-end tests pin base to `e2e_ubuntu_release`, so they never build base the way a user's first build does, from Ubuntu's newest cloud image and the mirrors' newest packages. An upstream change can break those builds before any test sees it. For example, vz's direct kernel boot needs an uncompressed arm64 kernel, and a VM shuts down only when its kernel has `gpio_keys`. `tests/e2e.sh --newest-base` builds base as a user's first build does and runs the checks that prove it works: `images`, then `project` (a VM that boots, stops, starts again and shuts down) and `tools`. `--only` chooses other sections in their place.

The run gives devvm no release to pin. It reads the newest release from Ubuntu's listing, as `scripts/bump.sh e2e-ubuntu` does, and prints it at its start next to `e2e_ubuntu_release`. It runs in a sandbox of its own, which is slot 0's with `-newest` added to its Lima home, state folder, Keychain service and lock (`~/.lt-e2e-go-newest`, `/tmp/devvm-go-e2e-newest`, `devvm-go-e2e-newest` and `/tmp/devvm-go-e2e-newest.lock`), with each fixed port slot 0's plus 1000. So the cached pinned images in the other sandboxes stay as they are. Each run first deletes its sandbox's images, tool images and package cache, so base is built from nothing, with its packages from the mirrors. The images section checks that devvm pinned the release Ubuntu listed as its newest and that base booted from it. When the newest doesn't boot, a user's devvm falls back to the release before it (`origin_no_boot`), so that check fails on the fallback. Its times go in `timings/plain-newest/` in slot 0's state folder, apart from the cached runs'. `--newest-base` can't be combined with `--slots` or `--slot`.

Run it before each release and every week or two between them, on an arm64 Mac (vz) and on a Linux host (QEMU) when you can, because the two boot base differently. At its end, it prints the release Ubuntu listed and the release devvm pinned. When a check fails, it says `UPSTREAM DRIFT` and names the release, because a user's first build of base gets the same failure now. Then:

1. Read the failed check's output and the run log of base's build, which the build's output names (`log_details`), in the sandbox's state folder under `data/devvm/logs/runs/`.
2. Run `tests/e2e.sh --only images` on the pinned release. If it passes, the failure is upstream's, from the newer image or its packages. If it fails too, the fault is devvm's own, so fix that first.
3. Fix devvm for the new release, such as a change to `assets/layers/base.sh` or to the Lima template. Then run `--newest-base` again until it passes.
4. Bump `e2e-ubuntu` to that release once it passes, so the other end-to-end runs test it too.

Until a fix ships, users can still build base, because devvm's fallback to the release before covers a newest release that doesn't boot. A package that breaks base has no fallback, so a fix for one goes in the next release.

## Releasing

- **Once, the keys:** a minisign key for releases, `minisign -G -p packaging/minisign.pub -s ~/.minisign/devvm.key` (commit `packaging/minisign.pub`; the secret key and its password never go in the repo), and a key git signs tags with (`git config user.signingkey`, GPG, or SSH with `gpg.format ssh`) that `git tag -v` verifies on this machine. Commit its fingerprint in `packaging/release-signer`, one per line (`#` comments): the GPG fingerprint (`gpg --fingerprint`, no spaces), or the SSH key's `SHA256:…` (`ssh-keygen -lf KEY.pub`). `release.sh` refuses a tag signed by any other key, even one git trusts. To rotate, add the new key's line, tag with it, then remove the old one.
- Bump `VERSION`, add the `CHANGELOG.md` entry, commit, then `git tag -s v<version>`.
- `scripts/release.sh` checks the tag with `git tag -v` and its signer against this checkout's `packaging/release-signer`, then builds `dist/` from the tagged commit with GoReleaser (`.goreleaser.yaml`), in a clone of its own, so only what's committed goes in, with one `goreleaser release --skip=publish`. It checks that the binary built for this host prints the version, then signs `SHA256SUMS` with `~/.minisign/devvm.key` (or `DEVVM_MINISIGN_KEY`) and verifies it with `packaging/minisign.pub`. Nothing is published.
- `dist/` then holds:

  | File | What |
  | --- | --- |
  | `devvm-<version>-<os>-<arch>.tar.gz` | the binary, its files (`assets/`) embedded, with `README.md`, `CHANGELOG.md` and `LICENSE`, for `darwin` and `linux`, `arm64` and `amd64` |
  | `devvm-<version>.tar.gz` | the source, which the Homebrew formula builds from |
  | `SHA256SUMS`, `SHA256SUMS.minisig` | their checksums, and the signature |
  | `install.sh` | the install script, set to this release and to `packaging/minisign.pub`'s key |
  | `devvm.rb` | the Homebrew formula, set to the source tarball's URL and checksum |

- `scripts/release.sh --head` builds from HEAD's commit instead, for testing, with `VERSION`'s version. It's unsigned unless `DEVVM_MINISIGN_KEY` names a test key; `DEVVM_MINISIGN_PUB` names its public key in place of `packaging/minisign.pub`. `DEVVM_RELEASE_URL` points the formula at a test location. A commit without `install.sh` is refused.
- To try `dist/install.sh` on such a build, copy `dist/` to `DIR/releases/download/v<version>/`, then in a throwaway `HOME` with `DEVVM_PREFIX` under it: `DEVVM_INSTALL_TEST=1 source dist/install.sh`, set `repo_url=file://DIR` and `protos='=https,file'` (it downloads over HTTPS only), and run `main --no-deps`. Without `--no-deps` it offers to install what the host lacks: answer no, or run it with no terminal.
- Every build sets the version with `-X github.com/w3cj/devvm/internal/cli.version=<version>`: devvm doesn't read `VERSION`. The formula (`packaging/homebrew/devvm.rb`) builds with Go the same way, installs the binary alone, and passes `brew audit --strict`.
- Attach the archives, `SHA256SUMS`, `SHA256SUMS.minisig` and `install.sh` to the GitHub release; `devvm.rb` goes in `devvmhq/homebrew-tap` as `Formula/devvm.rb`. Publishing is the maintainer's call: ask first.
