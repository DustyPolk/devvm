# Changelog

## 0.1.1-rc.2

A release candidate for 0.1.1, for trying the changes below before the release. It adds to 0.1.1-rc.1's changes. Install it with `devvm upgrade --to 0.1.1-rc.2`, with the install script's `--version 0.1.1-rc.2`, or with `brew install devvmhq/tap/devvm-rc`. Homebrew's `devvm` stays on 0.1.0. base installs the programs that transparent mode runs, so base and every image built on it are built again once.

- **Transparent mode:** on every tier but open, a tool that ignores the proxy settings, such as workerd under `wrangler dev`, a static Go binary or a container made through Docker's API, reaches the VM's proxy by the names it looks up (#35). In the VM every name resolves to the stand-in address `198.18.0.1`. Connections to it on ports 443 and 80, and on up to 32 ports your allow rules name, go to the proxy, which judges the host from the TLS server name or the HTTP `Host` against the same allowlist, with the same secrets and log. Other ports, UDP, protocols that name no host in their first bytes (such as Postgres and SSH), addresses, IPv6, names without a dot or under your network's search domain, and clients that don't trust the VM's CA still need the proxy settings. `devvm network transparent off` turns it off for one VM, and `transparent-proxy = false` in `config.toml` turns it off for every VM. A VM made from an image built before this lacks the programs, so each launch says so, and devvm update makes the VM again from a newer image ([tools that ignore the proxy](https://next.devvm.dev/docs/safety/network/#tools-that-ignore-the-proxy)).
- **The project folder's cache on Linux:** with Lima's default 9p cache, `mmap`, a file written in the project folder could reach this machine empty or cut to 4096 bytes, even after `fsync`, and SQLite and Gradle could read zeros (#36). New VMs on a Linux host use the cache mode `none`. A VM made before keeps `mmap` and warns at each launch until `devvm mount-cache none`, which a stopped VM gets at its next start and a running one after the restart devvm offers. With `none`, programs that map files for writing don't work in the project folder, SQLite's WAL mode among them, so keep such files on the VM's own disk or use a `--clone` VM. Where the folder can't be mounted again while the VM runs, such as on an Alpine `--from` VM, devvm restarts the VM once to apply the change. macOS VMs use virtiofs and don't change.
- **No strict `.git` protection:** in 0.1.0 and 0.1.1-rc.1, `devvm git-protect strict` set `diff.ignoreSubmodules = all`, which can't keep git on this machine out of a submodule the VM adds: a `.gitmodules` line the VM writes turns it back on, and `git add -A`, `git describe --dirty`, `git diff-index` and `git fetch` enter the submodule anyway (#37). `devvm git-protect` takes only `on` and `off`, and `strict` is a usage error that points to `devvm clone on`, which keeps the VM's code away from git on this machine. A VM that was strict shows as `on` at once in `devvm ls`, `devvm git-protect` and its `--json`, which never reports `"strict"`. The next launch, `devvm stop` or `devvm clone on` that finds it stopped takes out the value `all` that strict set and says so once. A value of `diff.ignoreSubmodules` you set yourself stays, where `devvm git-protect off` used to take out any ([VMs that were strict](https://next.devvm.dev/docs/safety/git-protection/#vms-that-were-strict)).
- **Folders of repos with `--clone`:** `devvm --clone` in a folder of repos gives one VM a clone of each repo you choose, in a picker or with `--repos`, at the same path as on your machine, so paths between the repos work in the VM, and a copy of the folder's own files. `devvm clone fetch` fetches every repo's work and lists the branches by name, and `devvm clone add PATH` copies one more repo (#3, [folders of repos](https://next.devvm.dev/docs/using/clone/#folders-of-repos)).
- **A `--clone` VM in a folder another VM mounts:** another VM's code could swap the repo under devvm's git, so `devvm --clone` and `devvm clone on` refuse such a folder, naming that VM. For a `--clone` VM made before, `devvm rm` runs no git in the repo on this machine: it asks before the clone's work goes, and without a terminal it refuses and keeps the VM, which `--no-clone-check` deletes.
- **Nested repos protected:** a VM over a folder of repos protects the `.git` of each repo nested in it, as far as 4 folders down and up to 100 repos, and names the repos it can't protect or that appear. A VM made before says once that its protection doesn't cover them, and `devvm git-protect on` protects them too. `devvm doctor` suggests `git config --global safe.bareRepository explicit`, so a folder that a VM makes look like a git folder can't take over git in the folders below it (#3).
- **`.git` protection on Linux:** a Linux host locks `.git` by pinning it read-only around QEMU in a user namespace, without root, and `devvm doctor` says why when a host can't, such as where AppArmor stops it (#4). A host that can't lock watches `.git` instead: each launch of a VM whose folder has a `.git` warns that the VM can change its hooks and config, and devvm names those that changed. `devvm git-protect off` stops the warning, and `devvm --clone` keeps a VM out of `.git`. On a host that can lock, a VM left off because it was made where devvm couldn't lock says that it can be locked now, with `devvm git-protect on` (#20).
- **Learning a VM's hosts:** `--network learn` runs a new VM on the internet tier while it records the hosts it reaches beyond its allowlist. `devvm network lock` picks which of them go into the VM's own rules, ticking only reviewed registries on port 443 and listing risky hosts apart, then gives the VM the allowlist tier (#17).
- **Rules by method and path:** a rule can narrow a host to some of its requests, such as `api.github.com GET,HEAD /repos/`, with `--method` and `--path` on `devvm network allow`, `deny` and `rm`. The proxy decrypts such a host's HTTPS with the VM's CA and judges every request on the connection. Allows add up and a deny beats any allow, so narrowing a host that's allowed whole, such as GitHub, takes a deny, such as `devvm network deny api.github.com --method POST,PUT,PATCH,DELETE`. `devvm network log` shows a blocked request's method and path.
- **Your own secrets:** `devvm secret set NAME --host HOST --env VARIABLE` saves a secret of your own, from a hidden prompt or `--stdin` and never the command line, and `devvm secret use NAME` gives a VM a placeholder in that variable. The VM's proxy puts in the value only for those hosts, over TLS on port 443, and `--method` and `--path` limit the requests that get it.
- **Logins carry only the fields devvm knows:** a VM's copy of Codex's `auth.json` and of Claude Code's `~/.claude.json` keeps only the fields devvm knows, and each launch names the fields it leaves out.
- **opencode withholds keys devvm doesn't bind:** as with pi, an opencode provider whose key devvm doesn't bind reaches the VM without its key, and the launch names the provider. To give a VM a provider's key as it is, such as a local model server's, list the provider under the agent in `config.toml`'s `[pass-keys]` (#30).
- **pi and more providers:** pi is a fourth coding agent (#23). The VM's proxy puts in Gemini, Groq, Mistral, xAI and DeepSeek API keys, as it does Anthropic's, OpenAI's and OpenRouter's, and a VM gets a placeholder in the shape the agent checks for (#31, #32). A key that a VM was given as it was before still works wherever the VM copied it, so make a new one for any VM you don't trust.
- **Each warning once:** a command prints each warning once, however many times it comes up, so a warning about the same line or file doesn't repeat. Warnings about different VMs or files still each print.
- **Nix 2.35.5:** the nix layer installs Nix 2.35.5, so images with it are built again once.
- **Prereleases on Homebrew:** `brew install devvmhq/tap/devvm-rc` follows release candidates, and `devvm` stays on the newest release (#19).
- **Fixes:** opencode's history copy works with SQLite 3.54 (#26), a VM's name leaves the NUL byte out of its ssh socket's path (#25), a build VM's ssh port is never the one its clone kept, a VM saves a login only for an agent it has (#27), and `.git` protection locks only real git folders, never a folder a VM names as one (#28).

## 0.1.1-rc.1

A release candidate for 0.1.1, for trying the changes below before the release. Install it with `devvm upgrade --to 0.1.1-rc.1`, or with the install script's `--version 0.1.1-rc.1`. Homebrew stays on 0.1.0.

- **A dotnet toolchain:** the .NET SDK is a shared toolchain, chosen by a folder's `*.sln`, `*.slnx`, `*.csproj`, `*.fsproj` or `global.json`, and a `global.json`'s `sdk.version` picks the SDK. devvm downloads Microsoft's archive for each platform and checks its SHA-512, global tools and workloads go to the VM's home folder, and the .NET CLI's telemetry is off ([toolchains](https://next.devvm.dev/docs/using/toolchains/)).
- **A network that inspects TLS:** devvm's own mise, which looks up the shared tools' versions on this machine, now trusts the CAs in `~/.config/devvm/ca` as well as the system's, so resolving works behind a proxy that re-signs HTTPS. When a certificate isn't trusted, devvm says so and points to the docs instead of saying to check the connection. On macOS, the CA also has to be trusted in the Keychain.
- **Release candidates:** devvm can ship prereleases, such as this one. `devvm upgrade --to` installs one, and devvm upgrade, the release check and the install script's default never pick one on their own.
- **Lima 2.2 or newer:** devvm needs Lima 2.2 at least, and it's tested with Lima 2.3. `devvm doctor` says when Lima is older.
- **Updated pins:** base's docker is 29.9.3, mise 2026.11.3, rustup 1.29.3, and tealdeer 1.9.1, with a newer oh-my-bash. The shared tools' backends are named, so mise's registry can't switch opencode to a source with no downloads. base installs ICU, which .NET needs, so base and every image built on it are built again once.

## 0.1.0

Released 2026-11-06.

The first release of devvm, which gives each project folder an isolated VM of its own, ready for you or a coding agent to work in. It runs on macOS 13 or newer and on Linux, on arm64 and x86_64, with Lima 2.0 or newer. It's tested on Apple silicon Macs and on Linux on both arm64 and x86_64, but not yet on Intel Macs.

- **A VM for each project folder:** running `devvm` in a folder makes its VM, or opens the one it has, and gives you a shell in it at the same path as on your machine. The VM mounts only that folder read-write, and with `--clone` it gets a clone of the repo of its own instead, whose work you fetch with `git fetch devvm`.
- **Ready in seconds:** every VM is a copy of a base image that devvm builds once, and the toolchains and coding agents are shared tools that VMs mount read-only. devvm detects node, python, rust and go from the project's files, and the built-in `docker`, `nix` and `desktop` layers, your own layers from `devvm layer new`, a project's `devcontainer.json` and `--from` with a container image change what a VM starts from.
- **Coding agents in the sandbox:** Claude Code, Codex and opencode run in the VM with your settings, skills and MCP servers. devvm keeps their settings and logins in a store of its own on your machine, `devvm agent import` copies them in from an agent you already use, `devvm agent login` makes an agent's login from the VM, and `devvm agent save` brings a VM's settings back to the store after you review the diff.
- **Network tiers and secrets:** every VM goes through a proxy that devvm runs for it, and its tier, which is open, internet, allowlist or none, decides what the proxy lets it reach. New VMs get the allowlist tier. On every tier, your secrets, such as your GitHub token and Claude Code token, stay on your machine, because the proxy puts them into the VM's requests.
- **`.git` protection:** on macOS, devvm locks a project's git hooks and config with a flag that even root in the VM can't clear, so code in the VM can't make your next git command on this machine run something.
- **Reaching VMs:** each running VM can be reached by name from ssh and from editors such as VS Code (`devvm code`), with your SSH agent only when you allow it. A VM forwards the ports you ask for, `devvm link` lets one VM reach a service that another VM publishes, and `devvm desktop` opens a VM's desktop in Screen Sharing on macOS, or serves it to a VNC viewer of your own on Linux.
- **Managing VMs and space:** `devvm ls`, `devvm stop`, `devvm restart`, `devvm update` and `devvm rm` manage VMs, and `devvm images`, `devvm gc`, `devvm space` and `devvm retention` show and clean up the images, shared tools and exports devvm keeps. devvm never deletes a project VM on its own, because it may hold unsaved work.
- **Installing and upgrading:** install devvm with Homebrew (`brew trust --formula devvmhq/tap/devvm`, then `brew install devvmhq/tap/devvm`) or with the install script, which checks the release's minisign signature and checksum and asks before it installs what devvm needs, such as Lima. `devvm doctor` checks this machine, and `devvm upgrade` installs a newer release once it has checked the signature.
- **For scripts:** many commands take `--json`, and `--no-input` makes devvm fail where it would ask, naming the flag that answers the question.
